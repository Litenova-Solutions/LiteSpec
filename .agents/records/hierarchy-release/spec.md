# Hierarchy, Naming and Book Release: Specification

**Date:** 2026-10-30. **Repositories:** LiteSpec `D:/Personal-Projects/LiteSpec` (branch `v3`), NightHall `D:/Personal-Projects/Nighthall` (branch `v1`).

This specification is the source the ledger slices point at. Part 0 is binding and wins over every later part where they differ. Parts A to F are the six planning sections, each written from the evidence in `.agents/delegate/hier/done/` (seven investigation reports) and checked by the judge; their facts and file references are current as of the date above.

## Part 0: Binding Decisions and Corrections

### The Owner's Decisions

1. **No record without a parent.** Every record of every type has exactly one parent: by identifier containment, by one required written up-link, or, for a type with no record above it, its layer list under the product. A record whose required parent is missing is an error at tier G, reported even when the record is a draft. The parent may itself be a draft, so an author may write top down or bottom up, but the structure is never incomplete. Every inverse link is computed, never written.
2. **Requirement origin.** Every requirement names its parent: a carrying `feature` (the limit to planned, later or refused features is lifted, so shipped features carry requirements too), or a constraint or research in `basedOn`, or a decision that names it in `decides`, in that precedence.
3. **Features advance goals.** A feature's link to a goal is renamed from `serves` to `advances`. Every feature names at least one problem in `solves`; its parent is the first. Every non-refused feature names at least one goal in `advances`. A refused feature names `refusedBecause` and the problem it declines in `solves`, and carries no `advances`.
4. **Journeys.** The journey's sentence field `goal` is renamed `aim`. Every journey names its goal record in a new required single link `serves: goal/<name>`, which is its parent. `finishedWhen` and the steps are unchanged.
5. **`serves` keeps one meaning per carrier:** a use case, reaction, job or screen serves journey steps; a journey serves one goal. Use cases no longer serve goals directly.
6. **Results and scenarios.** Written identifiers keep their form, `result/<use-case>.<name>` and `scenario/<use-case>.<name>`; use case names are unique, so the parent is readable from the identifier. Derived generic results take the same form (`result/<use-case>.forbidden`, `result/<use-case>.invalid-input`). A written result no scenario shows is reported: tier G for a success result, tier A for a refusal.
7. **Strictness by risk.** Every structural parent is tier G for all records. Other required links (coverage) are tier A for tier 3 records and tier G for tier 1 records, except where a decision above sets the tier explicitly.
8. **Field names: one concept, one name, one shape.** Renames: feature `state` to `lifecycle`; goal and requirement `by` to `dueBy`; feature `by` to `plannedFor` (a milestone or a date); decision `decided` to `decidedOn`; constraint `source` to `authority`; constraint `category` to `kind`. Glossary terms gain `layer` and `aliases` in the schema. The naming rule (a classifier is `kind`; a link is a present-tense verb, plural when it holds a list; a deadline is `<verb>By`, a recorded date `<verb>On`; a reason is `reason` or `<verb>Because`) becomes a provision whose mechanical half `litespec-maintain validate` checks.
9. **NightHall-only link fields:** `setting.readBy` (use cases that read the setting) is adopted into LiteSpec as a connection; NightHall drops `notification.sentBy` and `rule.writes`.
10. **The Links table** carries a "reads as" phrase in both directions for every link, and the book takes its connection labels from it.
11. **The book generator** (`litespec book`) is rebuilt to the approved mockup (`.agents/mockups/book-v6.html` and `.agents/mockups/book-v6/`), generated from the model.
12. **LiteSpec's own research and decisions** become records in the LiteSpec tree (Part A), and the research record gains a required `conclusion`.
13. No LiteSpec release is tagged or published by this work. No history, migration or compatibility material is kept in LiteSpec. NightHall migrates in the same plan.

### Corrections the Judge Made to the Sections

- **C1. No `product` field.** Part C proposes a new required `product` link on sixteen root types. It is not adopted: a project has exactly one product (`product-not-singleton` already guards that), so the field would repeat one value on every record, and LiteSpec generates derived facts instead of writing them. Instead, the model page states that the product is the parent of every record whose type has no record parent (goal, problem, constraint, decision, research, actor, term, module, role, permission, entry point, external system, runbook, integration event, deviation, known gap), and the book places them in their layer's type list under the product. The `record-without-parent` check covers only the types with a required written parent: feature (`solves`), requirement (origin), journey (`serves`), scenario (`result`), screen (`entryPoint`), and every identifier-contained type whose container is missing.
- **C2. Result and scenario identifiers.** Part F's grammar decision (`result/<module>.<use-case>.<name>`, renaming every written result and scenario) is overruled by decision 6: written identifiers stay; only the derived form changes, in the builder, and the few hand-written references to the old derived form are replaced mechanically.
- **C3. One parent code.** Requirement origin and the journey goal link are arms of `record-without-parent` (Part D); there is no `requirement-without-origin` and no `journey-goal-unlinked`.
- **C4. `solves` stays a list** with `minItems: 1`; the parent is its first entry (Part B), not a narrowing to one value (Part C).
- **C5. `result-without-scenario`** is tier G for success results and tier A for refusals (Part D).
- **C6. No `rule-fulfills-nothing`** in this release; a rule's parent is its identifier home.
- **C7. The book** is one offline shell with sharded data and no Mermaid (Part E).
- **C8. Execution order.** LiteSpec contract and research records first (Parts A, B), then checks and builder (Parts C, D), then the book (Part E), then NightHall (Part F). NightHall's founder decisions (journey goals, feature goals, requirement origins) are written as drafts with the founder as decider and listed for the founder, never decided by an agent.


## Part A: LiteSpec's Own Research and Decisions



**Top finding: LiteSpec's provisions are its only durable reasoning today, and they cannot carry it.** LiteSpec states in its own maintainer manual that it "holds no Intent or Behavior records of its own, because its provisions already are its specification" [[docs/core/maintaining.md:96](/D:/Personal-Projects/LiteSpec/docs/core/maintaining.md:96)]. Provisions state obligations; they have no home for a question, dated sources, or a conclusion that a later change can cite. This report decides three things: (1) the consumer `research` record needs a `conclusion` field it lacks today; (2) LiteSpec's own research and decisions should live as consumer-shaped records under `docs/intent/research/` and `docs/intent/decisions/`, checked by `litespec-maintain validate` and shown by the site as a non-applied area; (3) this release writes nine research records and nine decision records, listed exactly below. No build, test, linter, or project check was run in this investigation, per this run's rules; every command named below is for the executor and the judge.

Shared context read: [[.agents/delegate/plan/briefs/CONTEXT.md](/D:/Personal-Projects/LiteSpec/.agents/delegate/plan/briefs/CONTEXT.md)] (no `CONTEXT.md` exists at the repository root). Its settled decision 12 is the mandate for Part 2 and Part 3.

### Part 1: The Consumer `research` Record Needs a Conclusion Field

#### What the record holds today

The consumer research record carries a required frontmatter `question`, a required `sources` array, and one required body section, Answer. The schema requires `type`, `id`, `title`, `owner`, `status`, `sources`, and `question` [[schemas/record.schema.json:1540](/D:/Personal-Projects/LiteSpec/schemas/record.schema.json:1540)]; a source entry requires only `url`, with `read` optional [[schemas/record.schema.json:868](/D:/Personal-Projects/LiteSpec/schemas/record.schema.json:868)]. The template holds Answer plus optional Notes on Sources [[templates/consumer/research.md](/D:/Personal-Projects/LiteSpec/templates/consumer/research.md:30)], the consumer validator requires only the Answer H2 [[ConsumerValidator.Pages.cs:27](/D:/Personal-Projects/LiteSpec/apps/cli/src/LiteSpec.Cli/Consumer/ConsumerValidator.Pages.cs:27)], and the model checker requires `sources` with at least one entry and `question` [[Checker.cs:308](/D:/Personal-Projects/LiteSpec/apps/cli/src/LiteSpec.Cli/Model/Checker.cs:308)]. The provision states the same shape: a research record "MUST state its `question`, list each source with its read date, and carry Answer" [[docs/core/intent.md:141](/D:/Personal-Projects/LiteSpec/docs/core/intent.md:141)]. Three gaps follow. First, there is no conclusion anywhere a tool can read: Answer is body prose, and prose bodies never feed the approval hash, whose semantic fields for research are only `sources` and `question` [[Approver.cs:35](/D:/Personal-Projects/LiteSpec/apps/cli/src/LiteSpec.Cli/Model/Approver.cs:35)], so an approved record's actual finding can be edited without reopening its approval. Second, the book can render only `question` and `sources` for research [[BookPages.Fields.cs:59](/D:/Personal-Projects/LiteSpec/apps/cli/src/LiteSpec.Cli/Book/BookPages.Fields.cs:59)], so a decision citing research through `basedOn` points at a page whose takeaway no field states. Third, the schema does not enforce the read date the provision already requires: `read` is optional in `researchSource` [[schemas/record.schema.json:868](/D:/Personal-Projects/LiteSpec/schemas/record.schema.json:868)].

#### What NightHall's 29 records show

I read NightHall's research folder directly (`D:/Personal-Projects/Nighthall/docs/intent/research/`, 29 records plus its index, read 2026-10-30). Every one of the 29 carries an `## Answer` section. Sixteen of the 29 then add a second, conclusion-shaped H2 under drifting names: `What This Means for the Choice` (6 records), `What This Means for Each Choice` (4), and one each of `What This Means for the Model`, `What Follows for NightHall`, `Conclusion`, `The Position`, and `What This Record Changes`. The short ticketing records (for example `ticketing-accessibility.md`, read 2026-10-30) state their whole conclusion inside Answer and need nothing more; the long records (for example `acquisition.md` and `product-scope.md`, read 2026-10-30) separate "what the sources say" from "what this means for each choice" because their Answer runs to many pages. The register index then repeats the conclusions a third time: its "What the Register Currently Believes" table restates roughly one claim per record with a confidence and a required action, outside any record, unchecked and unhashed. All 125 source entries across the 29 records carry a `read` date (measured), 21 records are draft and 8 approved (measured), and 15 of 29 are cited by no other record's `basedOn` [[h-intent.md:89](/D:/Personal-Projects/LiteSpec/.agents/delegate/hier/done/h-intent.md:89)], which the investigation judges tolerated, not defective. The evidence is consistent: the finding lives in Answer, the conclusion migrates to an invented section or an index table, and nothing machine-readable holds it.

#### Decision 1: Add a `conclusion` Field, and Make `read` Required

Add one required frontmatter field to `researchPage`:

```json
"conclusion": { "$ref": "#/$defs/nonEmptyString" }
```

- **Exact change.** In [[schemas/record.schema.json](/D:/Personal-Projects/LiteSpec/schemas/record.schema.json:1540)]: add `conclusion` to the `researchPage` required array and properties; in `researchSource` [[schemas/record.schema.json:868](/D:/Personal-Projects/LiteSpec/schemas/record.schema.json:868)], make `read` required and allow exactly one of `url` (a web source) or `path` (a repository-relative evidence path), because LiteSpec's own research and NightHall's repository evidence ("From the repository means read in this repository with the path", `growth.md`, read 2026-10-30) cannot name a URL honestly. In [[templates/consumer/research.md](/D:/Personal-Projects/LiteSpec/templates/consumer/research.md:1)]: add `"conclusion": "<One sentence: what the sources establish and what follows>"` after `question`, and reword Answer's instruction to "Expand the conclusion: what the sources say, claim by claim, with the confidence behind each claim."
- **Statement change.** Amend `litespec/core/intent#record-research-with-read-sources` [[docs/core/intent.md:139](/D:/Personal-Projects/LiteSpec/docs/core/intent.md:139)] to: "A research record MUST state its `question`, state its `conclusion` in one sentence, list each source with its read date, and carry Answer." Add the term `conclusion` to the Concepts table on the same page and a `### Conclusion` entry to [[docs/reference/glossary.md](/D:/Personal-Projects/LiteSpec/docs/reference/glossary.md:547)] beside `### Research` ("The one sentence a research record concludes, stated as data so a decision can cite it."), placed alphabetically as the glossary contract requires.
- **Checks.** `litespec consumer` fails the page through the schema (required field, source shape); add `RequireString(record, "conclusion", findings)` to the research case in [[Checker.cs:308](/D:/Personal-Projects/LiteSpec/apps/cli/src/LiteSpec.Cli/Model/Checker.cs:308)] so `litespec model check` reports it with the other `record-shape` findings; add `conclusion` to the research list in [[Approver.cs:35](/D:/Personal-Projects/LiteSpec/apps/cli/src/LiteSpec.Cli/Model/Approver.cs:35)] so changing a conclusion reopens approval; add `"conclusion"` to the book's research field order with label `Conclusion` in [[BookPages.Fields.cs:59](/D:/Personal-Projects/LiteSpec/apps/cli/src/LiteSpec.Cli/Book/BookPages.Fields.cs:59)], and render a `path` source as code text beside the existing URL rendering in `RenderSource` [[BookPages.Fields.cs:1108](/D:/Personal-Projects/LiteSpec/apps/cli/src/LiteSpec.Cli/Book/BookPages.Fields.cs:1108)].
- **Rejected: a `## Conclusion` section.** NightHall's seven invented names for that section are the drift a section would codify; a section is prose, stays outside the approval hash, and cannot be rendered or cited as data. **Rejected: a record-level `confidence` field.** NightHall records carry per-claim labels (`observed`, `calculated`, `inferred`, each with its own confidence); one record-level value would falsify multi-claim records such as `market.md` and `regulation.md` (read 2026-10-30). Confidence stays in Answer, claim by claim.
- **Consumer cost.** NightHall writes 29 one-sentence `conclusion` fields, each lifted from its Answer's opening or its "What This Means" section; its 8 approved records need re-approval because the new field is semantic. The `read` tightening costs NightHall nothing: 125 of 125 source entries already carry one (measured).

### 4. The Naming Rule and Its `litespec-maintain validate` Check

#### 4.1 The provision (added in Section 1.1, placed beside `litespec/core/model#state-the-common-fields-on-every-record`)

**ID:** `litespec/core/model#name-each-field-for-one-concept`

**Statement:** Every field MUST be named for one concept and hold one shape on every record that carries it.

**Rationale (exact text to write):** One concept, one name, one shape, everywhere it appears. A classifier is `kind`. A link is a present-tense verb, plural when it holds a list, and a list of records named by their type takes the plural type name (`features`, never `feature`). A deadline is `<verb>By` and a recorded date is `<verb>On`, both ISO dates, except the declared date-or-milestone fields `dueBy` (goal, requirement) and `plannedFor` (feature), which hold a milestone name or a date as a plain string. A reason is `reason` or `<verb>Because`. A name already taken by a record type is never reused for a prose field. The mechanical half is checked (below); whether two fields with different names name one concept stays a reviewed judgement beside this provision. The named exceptions, and no others: `audience` (actor lists on product and notification, one permission on an integration event, following its published-fact framing), `code` (one refusal code on a result, a list of codes on a deviation), `subject` (record lists on a known gap and a deviation, the CloudEvents subject string on an integration event), `effectiveFrom` and `read` (dates whose names state what the date does, in `businessValue` and `researchSource`), and `readBy` (a link adopted under that name).

**Checked by:** `litespec-maintain validate` reports `FIELD_NAME_SHAPE` for a field whose name breaks the mechanical half of this provision.

LiteSpec today gives containment in the identifier: "Containment needs no link field: it follows the identifier" ([model.md](/D:/Personal-Projects/LiteSpec/docs/core/model.md:225)), with the identifier forms at [model.md](/D:/Personal-Projects/LiteSpec/docs/core/model.md:122) and the Links table at [model.md](/D:/Personal-Projects/LiteSpec/docs/core/model.md:186). Five rules extend that into a complete algebra. They are the whole decision; the table in Section 2 only applies them.

**P1. One parent, one placement.** Every record except `product` has exactly one parent record. The book places it exactly once, under that parent. Every other link on the record is a connection, rendered with its "reads as" phrase and never as a second placement. Every inverse link is computed, never written.

**P2. Containment first.** Where the identifier home segment, or the page home for a page or entry record, names one record, that record is the parent and no parent field is written. A use case page beside its aggregate is page containment; the builder already computes it as `AggregateOf` ([ModelBuilder.cs](/D:/Personal-Projects/LiteSpec/apps/cli/src/LiteSpec.Cli/Model/ModelBuilder.cs:517)).

**P3. One required up-link otherwise.** Where no containment names a parent, the child carries exactly one required, single-valued link field. List fields are trace, never parents, with two stated exceptions in P4.

**P4. Two multi-source parents, resolved by stated precedence, never by silence.** A requirement has three origin sources (Section 2) and a feature's carrying link is a list. Precedence and first-entry rules below pick the one parent in the open, in the checker and the book alike. Additional entries are connections. This replaces the builder's silent placed-once choice that [h-outline.md](/D:/Personal-Projects/LiteSpec/.agents/delegate/hier/done/h-outline.md:99) measured.

**P5. The product is the root, and the layers are not parents.** `product` has no record parent; its parent is the project that declares it, guarded by `product-not-singleton`. Intent, Behavior, Implementation, Proof, and Governance are transparent group nodes on the path from product to record. A group node is never a parent, never satisfies the parent rule, and is labelled only with a record type or the glossary term `layer`. This keeps `litespec/core/model#organize-the-book-by-the-record-layers` ([model.md](/D:/Personal-Projects/LiteSpec/docs/core/model.md:814)) and `litespec/core/model#name-book-labels-with-litespec-terms` ([model.md](/D:/Personal-Projects/LiteSpec/docs/core/model.md:826)) true at the same time.

Draft and retired handling is part of the algebra. A draft parent is a present parent: no finding on the child, and the child's effective status already reads draft through the parent chain ([model.md](/D:/Personal-Projects/LiteSpec/docs/core/model.md:290)). A retired record is exempt; it stands beside its replacement under the same parent. A retired parent still counts as present for a live child; authority checks, not this one, judge that.

Three rows deserve their reasoning stated, because the brief names them as the hard cases.

**Requirement.** The parent is the first satisfied source in this order: `feature`, `basedOn`, `decides`. `feature` wins because the carrying offer is the strongest origin, and lifting the shipped-feature limit (owner decision 2) makes it available to every requirement. `basedOn` follows because a constraint or research ground is an origin when no offer carries the commitment. `decides` is last and is the one inverse-read parent in the table: the decision writes `decides`, the requirement writes nothing back, and the checker computes the parent from that written link, so no second writing site exists. Inside a list, the first entry is the parent and later entries are connections; list order becomes meaningful, is covered by the approval hash, and authors who reorder a list know they move the placement. Today 2 requirements name two or more features, 23 name two or more `basedOn` entries, 11 name both sources, and the only 2 decision-decided requirements also name a `feature`, so precedence changes no NightHall placement; it only ends the silence. The requirement page and the topic segment are rejected as parents: a page style is not a record type.

**Feature.** `solves` narrows to exactly one problem. The evidence allows it at zero cost: every NightHall feature that names a problem names exactly one. One offer answers one pain; a second problem a feature touches is reached through the requirements that feature carries, which is where that trace already lives. A refused feature names the problem it declines in the same field, beside `refusedBecause`, so a refusal is a placement under the problem it refuses, not a root. `advances` (renamed from `serves`) must name at least one goal on every non-refused feature and must be empty on a refused one, but it is never the parent; it renders as a connection on the feature.

**Journey.** `serves` on a journey is single-valued by shape, although `serves` on a use case is a list of steps. The carrier rows already split in the Links table today, and one journey walks toward one goal by its own provision, so the singular shape states the rule instead of hiding it in a one-element list. The goal sentence survives as `aim`; the link, not the sentence, parents the journey.

### 5. The `record-without-parent` Finding

**Decision: one code for all types, not one per type.** The rule is one rule, and LiteSpec's own principle is one concept, one name. Per-type codes would add 33 entries to the tier map, 33 rows to the finding table, and 33 codes a known gap may name, to say the same sentence 33 times. The existing stock already works this way: `record-orphaned` covers five Behavior types under one code ([Checker.Graph.cs](/D:/Personal-Projects/LiteSpec/apps/cli/src/LiteSpec.Cli/Model/Checker.Graph.cs:195)), and the type and the missing field ride in the message.

**Specification.**

- Code: `record-without-parent`. Tier: **G**, added to `Tiers` ([Finding.cs](/D:/Personal-Projects/LiteSpec/apps/model/src/LiteSpec.Model.Core/Finding.cs:32)). It reads records only, always blocks, and exits nonzero even when the only findings are on drafts. Tier G severity has no draft softening ([Severity.cs](/D:/Personal-Projects/LiteSpec/apps/model/src/LiteSpec.Model.Core/Severity.cs:35) softens only tier S), which is what the settled decision requires.
- Subjects: every written record of every type except `product` and except retired records. Derived results are builder records, never written, and their parent exists by construction; they are out of scope.
- Fires when: a required parent field is absent or empty (`product`, `serves` on a journey, `solves` on a feature, `result` on a scenario); a requirement satisfies none of `feature`, `basedOn`, or an inverse `decides`; a containment home segment is missing, or names no record; a screen's `entryPoint` field disagrees with its identifier home, in which case it has two claimed parents and therefore no single parent. A use case always has at least its module, so it cannot fire on a use case whose identifier parses.
- Never double-fires: when an identifier cannot be parsed at all, this code reports the missing home and `identifier-form` stays silent for that home defect. When a parent field names a record that does not exist, `reference-unresolved` reports the dangling target and this code stays silent; absence and dangling stay two findings, as today.
- Draft parent: counts as a parent in full. A goal that is still a draft parents its journeys and drawn features without any finding; the child reads draft through effective status instead.
- Message form, following the stock: `Feature 'feature/x' names no parent: 'solves' names no problem.` Subject is the child identifier; path and line are the child's own.
- Known gaps: a gap naming `record-without-parent` with the child in `subject` covers it until `endsBy`, by the existing `check` plus `subject` mechanism; nothing new is needed. An expired gap fails as `known-gap-expired` does today.
- Out of scope by design: coverage links that are not parents. A feature missing `advances`, a written result shown by no scenario, and a job naming no runbook keep their own codes and their own risk-scaled tiers (tier A for tier 3, tier G for tier 1). Folding them into a parent code would make one code mean two things.

NightHall count on first run: **1,859 findings** (957 `product`, 719 requirement, 112 journey, 71 feature), all on records whose parent is either a codemod or a named judgement from Section 2.

### 6. Outline Rules the Book Follows from This Table

1. The outline root is the single product record. Under it sit four layer groups, Intent, Behavior, Implementation, and Proof, in that order, and one Governance group beside them. No other root exists.
2. A record's outline path is its parent chain with layer and type group nodes laid transparently on it. Group nodes are labelled with a record type or the glossary term `layer`, are never parents, and never satisfy the parent rule.
3. Intent runs: product, then goal (with its journeys under it), then problem (with its features, then each feature's carried requirements), then requirements parented by a constraint, a research record, or a decision under that origin, then constraint, research, product decision, actor. Features reaching a goal show `advances` as a connection on the feature, never as placement.
4. A requirement appears under its precedence parent from Section 2. Every losing origin renders as a connection with its "reads as" phrase. A requirement under a technical decision appears under that decision wherever the decision sits; its own layer label stays Intent.
5. Behavior runs: module, then aggregate, then use case, result, and scenario under the result it shows; reaction, job, notification, and setting under their module; rule under its identifier home; event under its aggregate; screen under its entry point. Roles, permissions, entry points, external systems, runbooks, and integration events list under the product inside Behavior, grouped and labelled by their record type.
6. Decisions split by home: product decisions in Intent, technical decisions in Implementation, both under the product. A replaced decision stands beside its replacement. A retired record shows under its parent with its retired status.
7. Terms render as one glossary beside the layers under the product, each showing its `layer` field. The glossary is never split.
8. Governance lists deviation and known gap entries beside the layers under the product. Subjects, provisions, checks, and end dates render as links. Nothing nests under a governance record and no governance record nests under a subject.
9. Implementation lists each code element under the record its mark names. Proof lists each test under the lowest record it proves and each finding under its subject; a finding with no subject lists under the product. Architecture layer, folder, and test project appear only as source text with the entry's file-and-line link.
10. Every non-parent link renders as a connection labelled from the Links table phrases in Section 3. Inverses are computed. No record appears twice.
11. A record the checker reports with `record-without-parent` has no outline node. The book build prints its identifier and the failed rule beside the finding. There is no stray sweep, no invented grouping, and no silent promotion to a root.

|---|---|---|
| One parent code or one per type | One code, `record-without-parent` | One provision, one tier, and per-type codes would multiply known-gap registry entries with no extra information, since the subject and message name the type and the expected parent. |
| Requirement origin code | No separate `requirement-without-origin`; it is the requirement arm of `record-without-parent` | The plan draft's proposed code and decision 1's parent code would report the same 719 records twice. |
| Journey goal code | No separate `journey-goal-unlinked`; it is the journey arm of `record-without-parent` | Decision 4 makes `serves: goal/<name>` a required structural link, so decision 1 already covers it at tier G. |
| Feature parent | The first `solves` problem is the parent; `advances` is a required trace, checked separately | Decision 3 names `solves` as the parent for a refused feature, and one parent rule for all features keeps the tree single-parented. |
| Root types | `product`, `goal`, `problem`, `constraint`, `research`, `decision`, `actor`, `module`, `role`, `permission`, `entry-point`, `external-system`, `runbook`, `integration-event`, `deviation`, `known-gap` and `term` are parented by their layer or list, not by a record | Their parent is the bounded context or a list page, which is not a record, so a record-parent finding on them could never be satisfied by writing a field. |
| Success versus refusal results | Decision 6 wins over decision 7 for `result-without-scenario`: success is tier G, refusal is tier A, at either risk tier | Decision 6 states the outcome split explicitly for this check, so it is the specific rule and decision 7 is the general one. |
| Rule `fulfills` | No `rule-fulfills-nothing` code in this release | No settled decision requires a rule to fulfill a requirement; the rule's parent is its identifier home, and the 2,052 direct-empty rules (53 empty even through governed use cases, my recount) are a policy question for a later decision. |

### 2. Architecture Decision

**One shell, sharded data, no fallback record pages.**

The generator writes a single `index.html` containing the mockup header, the three columns and an inline `BookData` registry stub. All other content arrives as `.js` shard files that call `BookData.put(key, value)`. Shards are loaded by inserting script elements, never by `fetch`, so the site keeps the current contract — "open the output folder's `index.html`", no server — under `file://` ([book.md](/D:/Personal-Projects/LiteSpec/docs/tools/book.md:27)).

| File | Loaded | Contents |
|:---|:---|:---|
| `index.html` | Always | Shell, registry stub, manifest script tag |
| `data/manifest.js` | Always | Project, roots, editor template, test run, totals, shard map |
| `data/lexicon.js` | Always | Type, link, field, glossary and section texts (Section 5) |
| `data/outline-<layer>.js` | Per layer, on first open | Nested outline tree for that layer |
| `data/records-<nnn>.js` | On navigation | Packed record detail objects, target 256 KB per shard |
| `data/search-<n>.js` | On first search | Title, type and statement excerpts per record |
| `data/queue.js` | On first queue, ballots or security view | Batches, ballot groups, security items |

Static fallback pages are rejected, with one exception: the shell carries a `<noscript>` note and the manifest summary (project title and record counts) as static text. Rendering every record twice — once as fallback HTML, once as client detail — would recreate the drift the rebuild removes, and the approved mockup has no no-script reading mode. Deep links survive as hash routes, `index.html#use-case/<module>.<name>`, which the mockup already uses for history ([script.js](/D:/Personal-Projects/LiteSpec/.agents/mockups/book-v6/src/script.js:1183)). The per-record `.html` URLs in the current [book.md](/D:/Personal-Projects/LiteSpec/docs/tools/book.md:15) contract are retired by the rewrite in Section 7; per the agent protocol, every citation of the old shape is replaced in the same change.

Mermaid is dropped. Aggregate pages render the mockup's state cards, flow table, data tables and rules table ([script.js](/D:/Personal-Projects/LiteSpec/.agents/mockups/book-v6/src/script.js:804)). This removes 5,494,801 bytes of vendored script from every generated book, removes a client rendering dependency, and keeps the lifecycle readable with scripting disabled in the shard data itself.

Fonts move offline: the mockup embeds Geist and Geist Mono as data URIs ([fonts.css](/D:/Personal-Projects/LiteSpec/.agents/mockups/book-v6/src/fonts.css:1)), while the current shell links Google Fonts ([BookRender.cs](/D:/Personal-Projects/LiteSpec/apps/cli/src/LiteSpec.Cli/Book/BookRender.cs:130)). The port ships the mockup font file as `assets/book-fonts.css` so the book is fully self-contained.

### 6. Mechanical or Founder, and the Order That Keeps the Check Honest

**Order.** N1 baseline, then the tool pin and N2, N3, N4 in one commit series with no model check claimed between the pin move and N3 (the new schema would correctly refuse every old identifier, which is an artefact of sequencing, not a finding), then a first full check. That check must show the baseline 2,711 open and 328 known, unchanged by code, plus only the intended new findings: requirement origin 719, journey goal 112, feature goal 28, refused-feature parent 71, deviation scope 5 — and no other new code. N5, N6 and N7 then burn those counts down in founder-approved passes, each pass followed by the same check, and each pass must leave every other finding count untouched; a change in any unrelated code is a defect in the script, not progress. N8 closes. Because the missing-parent check is tier G for all records including drafts, there is no intermediate state in which the check is green while founder rows are still open — by design, and stated here so nobody manufactures green: either the founder has decided a pass, or its count stands reported, named by record, with no known gap covering a founder choice the founder has not made.
