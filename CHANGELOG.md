### What a consumer of `dotnet-nextjs` does

A consumer selects `dotnet-react` in `standards.project.json` and accepts the six frontend pages as written. Each React frontend holds `src/app`, `src/routes`, and `src/modules`, composes one floorplan per route, and reads through a client generated from the API's published document. One shared UI package holds the registry source, the composites, the tokens, the source lock, and the design contract. The browser session is an HTTP-only cookie the API holds. There is no Auth.js extension to select.

### Provision identity

- Renamed every provision identifier from `AREA.PAGE.TOPIC.NNN` to `standards/<kind>/<page>.<heading-slug>`. The kind names the assertion class, the page segment is the `<area>-<stem>` of the owning page, and the slug is the kebab-case heading. An identifier therefore resolves to one heading with no lookup step. All 900 identifiers under `docs/` changed, and every citation in this repository and in a consumer changed with them.

## v1.16.0

- Added the `tutorial`, `how-to`, `reference`, and `command` page classes, and split the guide class into the first two of them. One class was carrying four jobs. Its contract, `Purpose, optional Prerequisites, Procedure, Verification`, was asked to hold a first lesson, a recipe for a known task, a list of settings, and a command reference, and each of those is read by a different person for a different reason. A tutorial ends in `What you built` rather than `Verification`, because verification asks whether a procedure worked and a tutorial asks what the reader now has. The how-to contract is the former guide contract under its own name, so `docs/guide/` needed no page moved.
- Mapped `docs/reference/` and `docs/tools/` to a page class, and widened the stem pattern that decides a class to accept a hyphen. The pattern had required a single lowercase word, which every descriptive file name fails, so `pageClass()` returned null for all three guide pages and for `audit-obligations.md`. The guide contract had therefore been enforced on no page in the tree since the class existed, and the four pages it was written for were the four it never read. Turning the reference directory on failed `audit-obligations.md` at once, and that page is now written to `Intent, Reference, optional Notes`.
- Added `standards/rule/core-authoring.name-the-tool-rather-than-the-mechanism`, `standards/rule/core-authoring.state-one-layer-per-page`, and `standards/rule/core-authoring.name-the-escape-from-every-abstraction`, which place a page at one layer and require every command page to name what it runs. A procedure that lists what a command already does becomes a second copy of that command, and the copy is the part that drifts. `Underneath` is a required section rather than an optional one, so a command page that hides its mechanism fails rather than passing in silence, and a command with nothing separately runnable writes `None.` under the existing empty-section rule. That makes the third provision static at no cost, where an optional section would have left it to review.
- Added `standards/rule/core-authoring.record-a-setting-as-reference` and the `configuration` kind behind it. A setting introduced inside whichever procedure needed it first is findable only by the reader who already knows which procedure that was. A configuration page carries the default, the scope, and what overrides each setting, and states its precedence order once rather than per setting.
- Added `standards/rule/core-authoring.route-the-reader-before-listing-pages` and `INDEX_MISSING_ROUTING`, which require the documentation root to name each page class before its first navigation group. A reader who cannot tell a tutorial from a reference opens both and trusts neither. The check confirms the block is present and positioned; whether a reader can act on it stays a review question, because no validator reads for comprehension.
- Added the `tutorial`, `how-to`, `reference`, `command`, and `configuration` consumer kinds, in `schemas/specification-metadata.schema.json` and in the `KINDS` map that holds the same rules a second time by design. A repository that ships a command had nowhere inside its documentation root to document it, so the command reference lived beside the code, outside the tree the validator reads, unchecked for vocabulary, prose, and link resolution. Each kind declares the H2 order its class answers at, which is the first time the consumer validator checks a section rather than a metadata field. A consumer tutorial had no kind that fit, and the nearest one, `section-index`, states that a page is a directory index. That is the misclassification `standards/rule/core-authoring.classify-every-specification-file` exists to refuse.
- Added `templates/standard/tutorial.md`, `templates/standard/command.md`, and the consumer templates for the three new kinds, and renamed `templates/standard/guide.md` to `how-to.md`. Added `docs/tools/`, which documents the five commands this repository ships as command pages. `tools/README.md` now links to them rather than restating them, which is the rule this release asks a consumer to follow.
- Added `standards/rule/core-system.state-one-occasion-for-every-behavior-specification`, `standards/rule/core-system.keep-a-scenario-informative`, `standards/rule/core-system.derive-every-scenario-from-one-reference-cast`, and the `scenario-cast` specification kind, which together require every module, aggregate, use-case, domain-policy, and end-to-end-flow specification to state one concrete occasion for its subject. Every section a specification already carried states a rule, a state, or a mapping, and none of them says when the behavior happens or who is under pressure while it does. In one consumer of 377 behavior specifications, not one page said what was going on in the world when its operation ran: a shortfall resolution was triggered by "somebody works through the open shortfalls", which names the mechanism and leaves the reader unable to tell that a customer had paid for stock that did not exist. A reader who cannot place an operation reads each of its rules as an arbitrary constraint. The cast is one record rather than a habit, because independent scenarios invent an organization and a customer per page and nothing then carries between two pages read in sequence.
- Bounded a `Scenario` section to 120 words in `standards/rule/core-system.bound-a-scenario-to-one-paragraph`, replaceable through `scenarioWordLimit` in `standards.project.json`, and refused a rule, acceptance, or end-to-end identifier inside one. Both bounds exist to keep the section from becoming a second specification: prose that grows past a paragraph becomes the page a reader reads instead of the tables, and an identifier inside a scenario reads as a second definition of the rule it names. The illustration has no authority, so a scenario that contradicts the page it sits on is the part that is wrong.
- Added a `Scenario` section to the module, aggregate, use-case, domain-policy, and end-to-end-flow templates, a `scenario-cast.md` template for the reference record, and a `Write the occasion before the rules` step to the domain modeling guide. Each template states what its own kind's scenario shows, because the occasion behind an aggregate is one instance moving through its states and the occasion behind a use case is one moment.
- Gave the consumer validator's case suite a third expectation form, `{ absent }`, for a diagnostic that must not appear. A case that narrows one setting can make an unrelated rule fire, and `no problems at all` then asserts the wrong thing: narrowing the documentation root put the reference cast outside the scan, which failed a case about an unscanned page.
- Split the contracts every layer names out of Application into a fifth baseline project, `Application.Abstractions`, and amended `standards/rule/backend-architecture.use-five-application-projects` to require it. Four projects left the cross-cutting contracts with nowhere to go but a folder inside Application, and a folder cannot decline what a developer puts in it. In one consumer that folder had reached 181 files and a tenth of the layer, with 23 children of which 8 carried the name of a sibling module, 99 files belonging to exactly one aggregate or module, and one file importing a use-case namespace. The project references Domain alone, so the compiler now refuses what review had been asked to catch: nothing in it can name a use case, a handler, or a module.

Placement had been a judgement call resolved by the word "shared", which is a claim about the future rather than a fact about the code, so it was never wrong at the moment it was made and always wrong later. Counting consumers is mechanical, and it derives the contracts project as the residue of the count rather than as a destination. Domain's shared kernel stays, because `standards/rule/backend-architecture.own-each-layers-contract-types` closes its membership.

Four different shapes for module-local code had grown in one consumer, including a `Shared` folder inside a module, and a folder named for a service reads exactly like a folder named for a use case until you open it.

The example had said "only for types used by multiple modules" in a closing sentence and shown a folder of technical kinds above it, and the picture is what gets copied.
- Made the consumer validator fail closed on an unclassified file, and added `standards/rule/core-authoring.classify-every-specification-file` to state the rule. A Markdown file with no metadata block was skipped in silence and the run still reported PASS, so an unvalidated specification was indistinguishable from a sound one. ## v1.8.0

- Replaced the module-first Domain folder convention with a top-down `module` then `aggregate` then detail hierarchy, replicated in every layer (`ARCH.MODULES.001` and its mirrored-folders convention). A module with more than one aggregate gives each aggregate its own folder with its own `Events/`, `States/`, and `Exceptions/`, and a closed set groups its base and cases in a folder named for the concept (for example `ScanResults/`) while the aggregate state hierarchy keeps its `States/` folder. A single-aggregate module keeps its aggregate flat. Kind-bucket folders (`Entities/`, `ValueObjects/`, `Services/`) and empty folders remain prohibited. The Application, WebApi, and Infrastructure layer conventions show the same module-then-aggregate nesting.
- Added `NAME.AGGREGATE.001`, which anchors every aggregate-owned type on its aggregate root's full name in first position: events (`OrganizationMemberAccessChangedEvent`), state cases (`PostPublishedState`, aggregate-first), union bases and cases (`RefundOutcome`, `RefundSucceededOutcome`), aggregate value objects (`OrganizationLegalProfile`), child entities, and exceptions. The full aggregate name is used, never an abbreviation, and the prefix chains to the aggregate root. Only Shared kernel types (`Money`, `EmailAddress`) are unprefixed, signaled by their location. The anchor is the aggregate root, not the module (`ReservationNotFoundException`, not `InventoryReservationNotFoundException`), while failure codes stay module-scoped; child-entity identities follow `{Aggregate}{Part}Id`. Domain events now carry the `Event` suffix (`{Aggregate}{PastFact}Event`); an event-reaction handler and its folder keep the `On{PastFact}` form without the suffix. Updated `DOMAIN.STATE.001`, `DOMAIN.CLOSEDSET.001`, `DOMAIN.EVENT.001`, the Domain names table, `NAME.SUFFIX.001`, and the affected examples across the profile and guides.
- Tightened `DOMAIN.EVENT.001` so a domain event carries no `Exception`, `DomainException`, or other error object and is not named after the language error type. A failure that is itself the recorded fact is modeled as immutable domain data (a value object or discriminated-union case) and carried as event data.
- Extended `NAME.EXCEPTION.001` to reserve the `Exception` suffix for `{DomainType}{Reason}Exception` failure types and to prohibit `Exception` as a domain business term for an anomaly or manual-handling case (for example `CancellationExceptionRaisedEvent`), with domain-word alternatives. The exception name anchors on the aggregate root, so an `Event` finance-assurance rule is `EventFinanceAssuranceMislabeledException`.
- Refined `NAME.AGGREGATE.001` from migration experience: a child entity with a first-class domain name (`Reservation`, a child of `CapacityPool`) is itself the anchor for its own states and unions (`ReservationHeldState`, not `CapacityPoolReservationHeldState`); a union case whose concept already embeds the aggregate reorders rather than doubles it (`SuppressionLegalBasis`, `RoleEventScope`); and a per-aggregate folder is named with the plural of the aggregate root so it adds a proper namespace segment (`{ProjectName}.Domain.Customers.CustomerAccounts`) that does not collide with the singular aggregate type (which a singular folder would, tripping CA1724).
- Tightened `DOMAIN.REPOSITORY.001` so a required load uses `GetByIdAsync`, which returns the aggregate and throws the aggregate's own `{Aggregate}NotFoundException` (a `DomainException` owning its code, mapped to `404`) from the Infrastructure implementation. A command handler no longer repeats a null check or builds a not-found failure with a hard-coded code and message at the call site. A nullable `FindBy...Async` is reserved for a genuinely optional lookup.
