# Generate

## Name

`litespec generate` writes the code the records fully determine, from the `generate` targets of the consumer declaration.

## Synopsis

```bash
litespec generate [--root <consumer>] [--check]
```

## Description

The command reads the built project model and writes one file set per `generate` target in `.litespec/project.yaml`. Each target names a `kind`, a `stack`, and the `path` folder the files go in:

- `refusal-codes` writes the refusal codes the records declare. For a .NET stack each module with refusals gets one C# file with a public static class holding one public const string per refusal, named from the refusal key in PascalCase with the code as its value and the refusal's meaning as its documentation. For a TypeScript stack the target writes one file with a const object of codes, their union type, and a map from each code to the English sentence its refusal results state.
- `permissions` writes the permission ids the same way: one C# constant class per module holding permissions, or one TypeScript file with a const object of ids and their union type.
- `event-decisions` writes, per module with domain events, one C# file with a static table holding each domain event the records declare with the outcome the outbox decision check derives from the records: `ignored` when the event record states `ignored: true`, `consumed` when a reaction or a translating event consumes it, and `missing` when the records state neither. A consumer's startup check compares its own decisions against this table instead of typed lists.
- `closed-sets` writes, per module or knowledge area holding closed value sets, one C# file with one partial abstract record per set and one sealed partial case per allowed value. A set is a reference-data table or a setting stating `choices`. The base name is the set name in PascalCase, and each case name is the base name with the value in PascalCase. The base exposes the stable `Code`, `FromCode`, `TryFromCode`, and `All` in code order. `FromCode` throws `ArgumentException` for an unknown code: an unknown label is malformed input, not a broken business rule, so a caller converts an untrusted label with `TryFromCode` and refuses through its own rule. Each case carries the meaning the record states for its value in `valueMeanings`. A hand-written sibling file may add members to any generated type.
- `knowledge-sets` writes, per area and variant, one C# file per reference-data table holding `row` and `columns`: a static partial class with a `Rows` list building each row of the variant through the model constructor, or the factory the table names, each row a call with named arguments from the column mapping. A column renders as the mapping states: a literal, a date, money or decimal construction, a typed key through the model's factory, a member of the model's closed set, a case of the model's nested closed set, a nested object from its sub-columns, a mapped literal, or a list of items rendering as its `items` states, object items each built from the entry's sub-columns. A column the row does not state renders as null, as does a nested object none of whose fields the row states; a stated list renders its items in written order, and an empty list renders empty. A table stating `singleton` holds one dated row with no key per variant and renders one `Value` instead of the `Rows` list.
- `exceptions` writes, per aggregate-declared refusal, one C# file with an internal sealed partial exception class named for the aggregate and the refusal, deriving from the target's `baseType`, carrying the code, the meaning as its message, and the rule mark the marks table requires. The mark names the rule naming the refusal, or the rule the use-case step cites beside the refusal's result. A refusal with `parameters` takes one string constructor parameter per value and interpolates the message. A refusal no rule enforces renders nothing, and the command lists it as `skipped <refusal id>: <reason>`; a refusal the steps link to several rules renders nothing as well, with each rule in the reason. A module-level refusal renders no file: the placement checks admit no per-module folder for its carrier, so it keeps a hand-written carrier.
- `domain-events` writes, per domain event, one C# file with an internal sealed partial record named for the aggregate and the fact, with one positional property per carried field in written order, implementing the target's `markerType`, documented from the meaning and carrying the event mark the marks table requires. An `id` becomes the typed identifier of what it identifies, or a `Guid` for any other target or with no `identifies`; a `choice` becomes the closed set it names; a `file` becomes the carried bytes as `byte[]`; an `integer` field stating `size: 64` becomes a `long`; a `map` field becomes a read-only dictionary of its value type by its key type; a list becomes a read-only list of its row, with a nested row record when the row holds more than one field, or of the named row type when the field states `rowType`; a row field of type list becomes a read-only list of its inner row, or of the named row type when the row field states `rowType`; a single object becomes its named row type, or a nested row record without one; a row field of type object becomes its named row type; a field naming an aggregate part or a C# type in `type` becomes that type; and a field with `required: false` becomes nullable. A hand-written sibling file may add members to any generated type. An event with a field of no known shape renders no file, and the record check reports the field.
- `module-events` writes, per module event, one C# file in an `On{Fact}` folder with a public sealed partial record named for the fact, with one positional property per published field in written order and types from the translated domain event, or from the field's own `type` when it states one, documented from the summary and carrying the event mark the marks table requires. The target's `markerType` is optional: a module event implements none when the target names none. A hand-written sibling file keeps the factory building the event from its domain event. An event whose translation or field resolves to nothing renders no file, and the record check reports it.
- `declarations` writes, per module with use cases, one C# file with an internal sealed partial class implementing the LiteBus `IMultiMessageDefinition`, declaring for each command and query what its record states: authorization from `access`, audit from `audit`, and idempotency from `idempotency`. The catalog resolves each message type with its namespace and members from the backend source the model reads, preferring the generated file when a generated and a hand-written file both declare the message, so every entry compiles against the message as declared. The authorization names one policy: the grant as a permission, signed-in, anonymous, system, or self form, wrapped for the tenant reach when the target names a form for it, and for a self scope, a recent sign-in, and system runs. The audit writes `Audited` with the use case id, category, and target kind, reading the target off the message when the record names one input, joining the listed inputs with a slash when the record names a composite target, and leaving the target to the handler when the record reads it from output, or `NotAudited` with the exemption reason. A keyed command keys through the message's real members from its key template with its scope, formatting the key culture-invariant with each date round-trip, replaying the first result exactly when the record states `returns-first-result`; a command of mode `state` or `none` exempts with its rationale. A hand-written sibling file may add members to the generated type. A use case the policy vocabulary cannot express, or whose message or member resolves to nothing in the backend source, renders nothing, and the command lists it as skipped with the reason.
- `validators` writes, per command and query carrying constrained inputs, one C# file in the use case `Application/` folder with an internal sealed partial validator class implementing the LiteBus validator for its message. Each constrained field renders one rule reporting a validity finding with the member, a stable reason code, and a message naming the field: presence for a required field the type admits missing, length and pattern for text, and span for numbers, comparing the amount of a money field, with a `map` field judging each value against the constraints of its value type. The pipeline refuses every finding through the derived `invalid-input` result. A constraint citing a rule that states a refusal renders no rule: Domain refuses it through its written result. A partial method hook runs the hand-written checks after the generated rules, and a hand-written sibling file may add members to any generated type. The validator carries no mark; the handler beside it carries the use case mark. A use case with no constrained input renders no file.
- `endpoints` writes, per module with HTTP-reached use cases, one C# file with an internal static partial class holding one nested endpoint class per use case, each implementing the platform endpoint contract. Each endpoint maps its route with its method, binds each input from its binding, builds the message, sends it through the LiteBus mediator, and answers the success status the outcome table assigns: a query, or a command stating a created location, projects its result with 200 or with 201 and the location, while any other command answers 204 with no body. A route input binds under its stated `routeParameter` when the record renames it, else under its input name. A choice input converts through its closed set first, and an unlisted label answers 400 before the message runs. A money input builds the shared money object from the bound amount with its fixed currency or its sibling value, or binds the amount as a decimal when the record takes its currency from an aggregate and the handler joins it from the loaded aggregate. A list input binds from the body as an array of request rows mapped each to the message row type: identifiers through their factory, closed sets through their code with an unlisted label answering 400, and money as a money input. A many-valued input binds from the body as an array, or from the query as a repeated query parameter. A file input binds from the multipart form as an upload and maps to the bytes the message carries. A `claim` input of identity type reads through the target's `claimReader`, one of boolean, text, or another non-identity scalar reads through the target's `claimValueReader`, a use case implying a tenant key reads it from the caller through the target's `tenantReader`, and a derived input the clock does not cover reads through a partial derivation method. A partial shaping method per projected result and a hand-written sibling file keep the response mapping and the derivations; the endpoint carries the use case mark. Each reader's namespace is imported in every endpoints file, so every reader sits beside the endpoint contract. A use case stating `generated: false` keeps its hand-written endpoint: downloads and sign-in redirects, and uploads the vocabulary cannot bind. A use case the endpoint vocabulary cannot express, such as a map input, a list outside the body, or a row the message gives no row type, renders nothing, and the command lists it as skipped with the reason.
- `messages` writes, per use case, one C# file in the use case `Application/` folder with an internal sealed partial record named for the use case and its kind: `<UseCase>Command` or `<UseCase>Query`, with the tenant key first when the tenancy selection implies one, one positional property per input in written order mapped through the record type table, the members the record implies (the idempotency key a keyed command computes from its key template, and the cursor or offset with the limit a paged query carries), the LiteBus message interface the target names over its result, and a row record beside it for each list or single-object input naming a row type. Each member takes the PascalCase field name. A `rowType` naming an aggregate part reuses that part's type, qualified with its declaring namespace, and writes no local row. A single object rides its named row type as one member, never a list. The tenant key rides the tenant aggregate's identifier type, or a `Guid` when no aggregate carries the term name; an input identifying the tenant aggregate carries the key itself, so no key is implied then. A `money` field rides the shared money object, or a decimal when the input takes its currency from an aggregate and the handler joins it, and a `file` field the carried bytes. An `integer` field stating `size: 64` rides a `long`, and a `map` field rides a read-only dictionary of its value type by its key type. An input stating `required: false` rides nullable whatever its origin, and any other input rides non-nullable. A hand-written sibling file may add members to any generated type. A use case with an input of no known shape, or a key template naming an input the message does not carry, renders no file, and the record check reports the input.
- `results` writes, per use case declaring an output, one C# file in the use case `Application/` folder with an internal sealed partial `<UseCase>CommandResult` or `<UseCase>QueryResult` record from its output: one positional property per field, a nested record per group when the output holds several groups or one optional, a row record beside it for each list or single object naming a row type, and the next cursor when the query pages by cursor. Each group type is qualified by the result type, since a nested type is not in scope in its own record header. Each member takes the PascalCase field name. A `rowType` naming an aggregate part reuses that part's type, qualified with its declaring namespace, and writes no local row. A single object rides its named row type as one member, never a list. An optional field rides nullable, as does an optional group. A `money` field rides the shared money object, and a `file` field the carried bytes. An `integer` field stating `size: 64` rides a `long`, and a `map` field rides a read-only dictionary of its value type by its key type. A hand-written sibling file may add members to any generated type. A use case with an output of no known shape renders no file, and the record check reports the field.

Every file opens with a header line saying `litespec generate` wrote it from the records, the LiteSpec version that wrote it, and that it must not be edited. Rendering is deterministic: modules, files, and entries order by identifier, so two runs write byte-identical files. A target with no entries writes no files.

For a .NET stack the `path` may hold `{module}` for the record module name or `{Module}` for the same name in PascalCase, and each module writes its file into its own resolved folder. Without a placeholder each module writes into `<path>/<Module>/`. A `knowledge-sets` target holds `{area}` and `{variant}` (or `{Area}` and `{Variant}`) instead, and each area and variant writes its files into its own resolved folder; without a placeholder each area and variant writes into `<path>/<Area>.<Variant>/`. An `exceptions`, `domain-events` or `module-events` target holds `{aggregate}` or `{Aggregate}` for the aggregate folder in both its path and its namespace, and each aggregate writes its files into its own resolved folder; a module event writes into an `On{Fact}` folder under it. A `validators` target writes each validator into the `Application/` folder of its use case under the resolved path. A `messages` or `results` target holds `{aggregate}` or `{Aggregate}` for the aggregate folder and `{useCase}` or `{UseCase}` for the use-case folder in both its path and its namespace, and each use case writes its files into its own resolved folder; a module-level use case drops the aggregate segment. An event, `messages`, or `results` target lists in `usings` the C# namespaces its files import for referenced identifier, value, and part types; a `validators` target lists the namespaces of messages declared outside their use case folder. The `namespace` names the C# namespace with the same placeholders. For a TypeScript stack the target writes its one file directly into `path`, which holds no placeholder.

A `declarations` target names the policy vocabulary its project's guard evaluates: `permissionPolicy` turns a permission grant into a policy name with `{permission}` for the permission id or `{name}` for the name after the prefix, `signedInPolicy`, `anonymousPolicy`, and `systemPolicy` name the policy for each grant, and `selfPolicy`, `recentSignInPolicy`, and `runsAsPolicy` wrap a policy with `{policy}` for the wrapped policy and `{window}` for the sign-in window. A target whose calls at one tenant reach need a distinct policy names a wrap for that reach in `crossPolicy`, `publicPolicy`, or `nonePolicy`, each with `{policy}` for the grant's policy; the tenant wrap applies first, before the self, recent-sign-in, and system-run wraps. Each form is optional; an unset form reads the default the .NET application page documents, and an unset tenant form leaves the grant's policy unwrapped. A use case whose tenant names no known scope, whose grant names no known form, whose access states an authorization condition, whose audit level `none` carries no exemption rationale, or whose message type, key placeholder, or audit target resolves to nothing in the backend source renders nothing: the command lists it as `skipped <use-case id>: <reason>`, and a module whose every use case skips writes no file.

An `endpoints` target names in `claimReader` the qualified static method reading an actor identity, as `Namespace.Type.Method`, taking the caller and the actor name the record states. The method answers the identity the message carries for a `claim` input of identity type. The target names in `claimValueReader` the qualified generic static method reading a non-identity claim value, as `Namespace.Type.Method`, taking the caller and the claim name and answering the value parsed as its type argument. The method answers the value the message carries for a `claim` input of boolean, text, or another non-identity scalar type; without it, such a use case renders nothing. The target names in `tenantReader` the qualified static method reading the tenant identity, as `Namespace.Type.Method`, taking the caller. The method answers the tenant key the message carries first for a use case implying one; without it, such a use case renders nothing. The target lists in `usings` the C# namespaces its files import for referenced identifier, money, closed-set, and response types. A file input binds from the multipart form as an upload. A use case carrying a map input, an object input, a list outside the body, a list reusing an aggregate part, a multi-field list naming no row type, a many-valued file, a many-valued claim, a many-valued route or header input, a choice naming no closed set, a claim input of choice, money, file, list, map, or object type, a scalar claim input without a `claimValueReader`, a money input taking its currency from an optional sibling, a list row of list, map, file, or object type, a list row holding many values, a list row naming no closed set, a list row taking its currency from an optional sibling, a file beside body inputs, or an implied tenant key without a `tenantReader` renders nothing: the command lists it as `skipped <use-case id>: <reason>`, and a module whose every use case skips writes no file. A use case stating `generated: false` is left out silently.

A `messages` target names in `commandInterface` and `queryInterface` the LiteBus message interfaces its commands and queries implement over their results; a message implements none when the target names none. A `messages` or `results` target renders the use cases of the module, or with `visibility: public` the use cases another module reaches as public records, with the public result named without the kind (`<UseCase>Result`), so a project pairs an internal target writing into `Application/` with a public target writing into the Contracts project.

With `--check` the command writes nothing, lists each file it would write or rewrite, and exits 1 when any would change. Skipped use cases and refusals list in either mode.

When a record file does not parse, the command writes nothing, names each invalid file, and exits 2, so a generated file is never quietly short. When a target names an unsupported kind or stack combination, the command writes nothing and names each invalid target. When a target writes inside another tool's output folder or two targets write the same file, the command writes nothing, names each offending target, and exits 2.

## Arguments

None.

## Options

| Option | Default | Effect |
|:---|:---|:---|
| `--root <consumer>` | the working directory | The folder to start from. The command uses the first folder at or above it that holds `.litespec/project.yaml`. |
| `--check` | off | Writes nothing, lists each file that would change, and exits 1 when any would. |
| `--help` | off | Prints the usage text and exits 0. |

## Exit Codes

| Code | Meaning |
|:--|:--|
| `0` | The files are written, or `--check` found every file current. |
| `1` | A file would change with `--check`, a target is invalid, the records cannot be read, or a file cannot be written. |
| `2` | The arguments are wrong, the root holds no project file, a record file does not parse, or a generate target writes inside another tool's output folder or the same file as another target. |

## Examples

Write the code the records determine:

```bash
litespec generate --root ../consumer
```

List the files that would change, without writing:

```bash
litespec generate --root ../consumer --check
```

## Underneath

The command opens the consumer through the same root walk `litespec model check` uses, builds the project model, and renders every configured target in memory. `litespec model check` renders the same plan and reports each missing or differing file as a `generated-drift` finding, so the check fails exactly when `generate` would write. Nothing beneath this command is separately runnable.
