# Sync

## Name

`litespec sync` writes the pure data the records determine, from the `sync` targets and the frontend clients of the consumer declaration.

## Synopsis

```bash
litespec sync [--root <consumer>] [--check]
```

## Description

The command reads the built project model and writes one file set per `generate` target in `.litespec/project.yaml`, plus the TypeScript tables of each frontend that names a client. Each target names a `kind`, a `stack`, and the `path` folder the files go in:

- `refusal-codes` writes the refusal codes the records declare. For a .NET stack each module with refusals gets one C# file named `<Module>RefusalCodes.cs` with a public static class holding one public const string per refusal, named from the refusal key in PascalCase with the code as its value and the refusal's meaning as its documentation.
- `permissions` writes the permission ids the same way: one C# file named `<Module>Permissions.cs` per module holding permissions.
- `event-decisions` writes, per module with domain events, one C# file named `<Module>EventDecisions.cs` with a static table holding each domain event the records declare with the outcome the outbox decision check derives from the records: `ignored` when the event record states `ignored: true`, `consumed` when a reaction or a translating event consumes it, and `missing` when the records state neither. A consumer's startup check compares its own decisions against this table instead of typed lists.
- `closed-sets` writes, per module or knowledge area holding closed value sets, one C# file named `<Module>ClosedSets.cs` with a static class holding one nested class per set, each with one const string per allowed value. A set is a reference-data table or a setting stating `choices`.

For each frontend whose project file entry names a `client`, the command also writes three TypeScript files beside the client at `<client package>/src/litespec/`:

- `refusals.ts` holds every declared refusal code as a const array with its `RefusalCode` union type.
- `permissions.ts` holds every declared permission id as a const object with its `PermissionId` type.
- `capabilities.ts` maps each screen route to the permissions the use cases the screen offers need, typed against `PermissionId`.

A C# target with no module holding its kind writes no files, and a TypeScript table with no entries writes no file. Rendering is deterministic: modules, files, and entries order by identifier, so two runs write byte-identical files.

Every file opens with a header line saying `litespec sync` wrote it from the records and naming the command to rerun, followed by `// <auto-generated/>`. The header carries no tool version. On its first run in a consumer, the command deletes the matching old `<Module><Kind>.generated.cs` file it replaces.

For a .NET stack the `path` may hold `{module}` for the record module name or `{Module}` for the same name in PascalCase, and each module writes its file into its own resolved folder. Without a placeholder each module writes into `<path>/<Module>/`. The `namespace` names the C# namespace with the same placeholders. A `svelte` stack target writes nothing: the frontend clients own the TypeScript tables now.

With `--check` the command writes nothing, lists each file it would write, rewrite, or delete, and exits 1 when any would change.

When a record file does not parse, the command writes nothing, names each invalid file, and exits 2, so a synced file is never quietly short. When a target names an unsupported kind or stack combination, the command writes nothing and names each invalid target.

## Arguments

None.

## Options

| Option | Default | Effect |
|:---|:---|:---|
| `--root <consumer>` | the working directory | The folder to start from. The command uses the first folder at or above it that holds `.litespec/project.yaml`. |
| `--check` | off | Writes nothing, lists each file that would change, and exits 1 when any would. |
| `--help` | off | Prints the usage text and exits 0. |

## Exit Codes

| Code | Meaning |
|:--|:--|
| `0` | The files are written, or `--check` found every file current. |
| `1` | A file would change with `--check`, a target is invalid, the records cannot be read, or a file cannot be written. |
| `2` | The arguments are wrong, the root holds no project file, or a record file does not parse. |

## Examples

Write the pure data the records determine:

```bash
litespec sync --root ../consumer
```

List the files that would change, without writing:

```bash
litespec sync --root ../consumer --check
```

## Underneath

The command opens the consumer through the same root walk `litespec model check` uses, builds the project model, and renders every configured target and every frontend client in memory. `litespec model check` renders the same plan and reports each missing, differing, or replaced file as a `sync-drift` finding, so the check fails exactly when `sync` would write. Nothing beneath this command is separately runnable.
