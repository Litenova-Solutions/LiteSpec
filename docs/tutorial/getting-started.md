# Start a Consumer Repository

## Purpose

A LiteSpec consumer is a project built against the LiteSpec standard, and this tutorial turns an empty folder into one: its configuration, its first Intent records, the Behavior specified from them, one working use case, and a passing model check. A use case names what the product does for an actor, a person or system using it, and the model check confirms the records, code, and tests agree. This tutorial follows one backend stack and one frontend stack, the `dotnet` backend with a React frontend, so every step runs the same way for every reader. A developer follows these steps once, when creating the consumer. Each step names the standard it satisfies, and the tutorial adds no rule of its own.

## Prerequisites

- Read the [agent protocol](../core/agent.md), the [authoring standard](../core/authoring.md), and the [supported scope](../core/scope.md) to learn how agents work, how pages are written, and what one project covers.
- Read the [extension catalog](../ext/README.md) to learn which capabilities stay inactive at the start.
- Install the .NET SDK and Node.js releases the adopted release pins under `stack` in its `litespec.manifest.json`.
- Ship the `dotnet` backend with a React frontend: this tutorial follows that pair from the `dotnet-react` preset. When the product ships another frontend, follow this tutorial first, then declare that frontend with its own how-to, [Add a Svelte Frontend](../guide/add-a-svelte-frontend.md) or [Add a Blazor Frontend](../guide/add-a-blazor-frontend.md).

## Lesson

1. Install the LiteSpec release as a local .NET tool: run `dotnet new tool-manifest` when the folder has no `.config/dotnet-tools.json` yet, then `dotnet tool install LiteSpec.Cli --version 3.0.0` and `dotnet tool restore`. From here on, run every command below as `dotnet litespec <command>` from the consumer root. This satisfies `litespec/workspace/structure#use-the-canonical-root-tree`.
2. Write the project configuration: run `dotnet litespec init --preset dotnet-react --size small`, which writes `litespec.project.json` with the shape, the stacks, and the adopted release in `reviewedLiteSpecVersion`, with the `## LiteSpec` block in `AGENTS.md`, the glossary, and the example cast beside it. Fill every placeholder and name every owner. This satisfies `litespec/core/scope#select-a-size-a-shape-and-stacks`.
3. Select extensions only when their criteria already hold. Write each selection in the object form with its criterion and review date. This satisfies `litespec/core/scope#select-conditional-extensions-explicitly` and `litespec/core/scope#record-selected-extensions`.
4. Record how the project reviews and adopts: name the security reviewer and the veto window in days in `review`, point `paths.behaviorDocs` at the Behavior root, and name the decision that ends transcription mode in `adoption.transcriptionEndsWith`. This satisfies `litespec/core/scope#record-the-review-configuration`, `litespec/core/scope#point-behavior-docs-at-the-behavior-root`, and `litespec/core/scope#record-the-transcription-endpoint`.
5. Create the toolchain configuration from the manifest pins. Add the SDK floor, the shared build settings, the central NuGet versions, the tool manifest, and the JavaScript toolchain pin. This satisfies `litespec/backend/dotnet/config#set-the-sdk-floor-at-the-workspace-root`, `litespec/backend/dotnet/config#centralize-net-build-settings`, `litespec/backend/dotnet/config#centralize-nuget-versions`, `litespec/backend/dotnet/config#commit-the-tool-manifest`, and `litespec/workspace/config#pin-the-javascript-toolchain`.
6. Add only the packages the manifest already pins. Record each new package approval explicitly. This satisfies `litespec/backend/dotnet/packages#pin-every-dependency-centrally` and `litespec/workspace/dependencies#approve-new-packages-explicitly`.
7. Create the API solution. Add the five application projects, the AppHost, the ServiceDefaults, and the Architecture and Integration test projects. Add the Acceptance project when the product needs executable specifications. Reference `LiteSpec.Analyzers` from the five application projects, or once in `Directory.Build.props`:
   ```xml
   <ItemGroup>
     <PackageReference Include="LiteSpec.Analyzers" Version="3.0.0" PrivateAssets="all" />
   </ItemGroup>
   ```
   This satisfies `litespec/backend/dotnet/architecture#use-five-application-projects`, `litespec/backend/dotnet/testing#keep-the-test-projects-the-size-requires`, and `litespec/backend/dotnet/packages#run-litespecanalyzers-in-every-application-project`.
8. Apply the naming rules: match each C# file to its primary type and each namespace to its folder. This satisfies `litespec/backend/dotnet/naming#match-c-files-and-primary-types` and `litespec/workspace/naming#keep-namespaces-aligned-with-folders`.
9. Write the product brief. Copy `product-brief.md` from the template index to `docs/product/brief.md`. State the boundary, the refusals, and the audience. This satisfies `litespec/core/intent#state-one-product` and `litespec/core/intent#keep-intent-in-its-homes`.
10. Write one requirement page. Copy `requirement-page.md` from the template index to `docs/product/<area>/<topic>.md`. State each commitment as one requirement with its kind, `functional`, `quality`, or `business`, its exceptions with their fallback, who sets its values, and its risk where one applies. This satisfies `litespec/core/intent#shape-each-requirement-page`, `litespec/core/intent#identify-every-requirement`, and `litespec/core/intent#state-each-exception-with-its-fallback`.
11. State which constraints apply. Write one constraint record per outside rule, with its source and category, or record that none applies, and set `constraints.answered` to `true`. This satisfies `litespec/core/intent#answer-every-constraint` and `litespec/core/scope#answer-the-constraints-question`.
12. Record the first decision. Copy `decision.md` from the template index to `docs/product/decisions/<number>-<name>.md`. Name the options with what speaks for and against each, the decider, and what would change the choice. This satisfies `litespec/core/intent#record-each-choice-as-a-decision`.
13. Write the people records. Add one actor page per party, one role page per grantable set, and the permission entries on the permissions page. Each use case later declares its access against one of those permissions. The `actor.md`, `role.md`, and `permission-list.md` templates define the fields. When the slice exchanges anything with an outside system, add an external system page for it with its operations and erasure.
14. Write one journey. Copy `journey.md` from the template index to `docs/product/journeys/<name>.md`. State the goal, the observable `finishedWhen`, and the steps as product sentences with ids, each with its actor and what the person experiences when it goes wrong. Steps name no use case; use cases point up to them later with `serves`. This satisfies `litespec/core/intent#order-each-journey-toward-one-goal`, `litespec/core/intent#write-journey-steps-as-sentences-with-ids`, and `litespec/core/intent#state-when-each-journey-finishes`.
15. Group the open questions into ballots. On each draft record, name the question, its decider, its date, the recommendation, and the ballot it joins, so the founder decides each ballot in the book. This satisfies `litespec/core/intent#group-questions-into-ballots`.
16. Specify the module from Intent. Follow [Model a Behavior Module](model-domain.md) for the module, the aggregates with their data classes, the rules, the use cases with their access, consistency, and effects, the scenarios, the events, the reactions, jobs, notifications, and settings, and the retention rows. This satisfies `litespec/core/system#group-module-use-case-files-by-aggregate` and `litespec/core/model#author-one-slice-at-a-time`.
17. Implement one use case. Move the transition into a business method, keep the handler narrow, commit once, expose one endpoint, and authorize the target. Code points up to its record through its folder. This satisfies `litespec/backend/domain#express-transitions-through-business-methods`, `litespec/backend/application#keep-command-handlers-narrow`, `litespec/backend/dotnet/persistence#commit-once-in-the-command-pipeline`, `litespec/backend/dotnet/api#use-one-endpoint-per-operation`, and `litespec/quality/security#authorize-each-target-resource`.
18. Declare the React frontend. Declare the application tree and mirror the backend use case path. This satisfies `litespec/frontend/web/structure#use-the-frontend-application-tree`. Compose each route from one floorplan. This satisfies `litespec/frontend/web/ui#compose-each-route-from-one-floorplan`.
19. Deliver one complete slice. Ship source, tests, contracts, and operating evidence for one use case. This satisfies `litespec/core/system#deliver-one-complete-use-case`.
20. Add the operating records. Write the settings and runbooks, add deployment, backup, restore, and rollback, and configure the pipeline gates. This satisfies `litespec/quality/operations#start-the-stack-with-one-local-command` and `litespec/quality/ci#run-applicable-gates-on-every-pull-request`.
21. Build the model. Run `dotnet litespec model build` from the consumer root. It writes `model.json` with the computed links between records, code, screens, and tests.
22. Check the model. Run `dotnet litespec model check`. It prints a tier beside each finding and exits 1 on any unresolved citation, missing link, undeclared edge, or unproved scenario. Fix every finding before continuing.
23. Render the generated regions: run `dotnet litespec model render`, then commit what it wrote.
24. Run the remaining validators. Run `dotnet litespec consumer` and `dotnet litespec ui` from the consumer root. Both exit `0` on a clean tree. This satisfies `litespec/core/release#run-consistency-checks`.
25. Read the book. Run `dotnet litespec book --model .model/model.json --out .book` and open the journey chapter with its ballots, the way product reviewers read the change. This satisfies `litespec/core/release#review-intent-changes-through-the-intent-diff-and-ballots`.

## What You Built

- A consumer repository at small size that the model check accepts.
- One implemented use case with Intent, Behavior, code, tests, and generated contracts.
- When the product ships another frontend, [Add a Svelte Frontend](../guide/add-a-svelte-frontend.md) and [Add a Blazor Frontend](../guide/add-a-blazor-frontend.md) declare it. The checks are documented on [Validate Consumer](../tools/consumer.md) and [Validate Controlled UI](../tools/ui.md); all commands are listed on the [command index](../tools/README.md).
