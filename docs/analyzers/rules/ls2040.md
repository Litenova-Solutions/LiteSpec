# LS2040: Knowledge Key Built from a String Literal

LS2040 reports a knowledge key built from a string literal outside a knowledge set. Code reads knowledge by role and date through the model, so a literal key bypasses the lookup the model owns and pins the caller to one data key.

## Reference

### What the Rule Enforces

LS2040 enforces [Read Knowledge by Role and Date](../../backend/knowledge.md#read-knowledge-by-role-and-date) (`litespec/backend/knowledge#read-knowledge-by-role-and-date`). It runs in every layer except Test. Its category is `LiteSpec.Layers`. Severity and enablement follow the [Analyzers overview](../README.md).

### What the Rule Reports

A creation `new SomeKey("literal")` or a call `SomeKey.Parse("literal")` or `SomeKey.From("literal")` reports when an argument is a string literal and the type is a knowledge key: a type implementing an interface whose name ends in `KnowledgeKey`, or a type named `*Key` in a knowledge model project. The diagnostic sits on the type name of a creation or the method name of a call, and its message names the key.

### Failing Example

```csharp
namespace Claimwick.Spending.Application.SubmitExpense;

internal sealed class SubmitExpenseCommandHandler
{
    public void Handle()
    {
        var key = new CountryKey("FR");
    }
}
```

with `CountryKey` declared in the `Claimwick.Travel` knowledge model project.

### Passing Example

```csharp
namespace Claimwick.Spending.Application.SubmitExpense;

internal sealed class SubmitExpenseCommandHandler
{
    public string Handle(CountryKey key)
    {
        return key.Code;
    }
}
```

The key arrives from the caller, which read it by role and date through the model.

### How to Fix

Resolve the key through the model's runtime by role and date, and pass keys into the code that needs them instead of building them from literals.

## Notes

### What the Rule Ignores

A creation or call in a Test file, in a knowledge set file, or in a file the layer rules cannot place, never reports. The rule leaves alone an argument that is no string literal, a method other than `Parse` or `From`, and a type named `*Key` outside a knowledge model that implements no `*KnowledgeKey` interface. The rule runs in knowledge model files too: only set files are excluded.
