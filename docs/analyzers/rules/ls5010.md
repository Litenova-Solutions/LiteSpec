# LS5010: Permission Opens with an Undeclared Verb

## Intent

LS5010 is a compiler check that reports a permission record whose name opens with a verb the use-case vocabulary does not declare, because the generator derives whether the permission only reads from its leading verb. This page states what the rule reports, where the error sits, and how to declare the verb or rename the permission.

## Reference

### What the Rule Enforces

LS5010 enforces [State the Scope of Every Permission](../../core/access.md#state-the-scope-of-every-permission) (`litespec/core/access#state-the-scope-of-every-permission`). It runs in Domain, Application, Infrastructure and WebApi projects, where the generator writes permission metadata. Its category is `LiteSpec.Traceability`.

### What the Rule Reports

The generator reads each permission name's first word, or the phrasal verb it opens with, against the use-case verb table, the permission-only word `manage`, and the project's vocabulary additions. A permission whose first word is no known verb reads as not reading, and the rule reports it, naming the permission and the word. The diagnostic has no source location, because the unknown word lives in the records.

### Failing Example

The permission list holds `permission/frobnicate-widgets`: `frobnicate` is no baseline verb and the project vocabulary declares no such verb, so the entry reads `Reads` false and the rule reports.

### Passing Example

The permission list holds `permission/read-loans`: `read` is a baseline reading verb, so the entry reads `Reads` true and the rule stays silent. A permission opening with a project verb the vocabulary declares, such as `permission/borrow-book` with `borrow` in `verbs`, reads `Reads` false and the rule stays silent, and so does `permission/manage-copies`, which opens with the permission-only word `manage`.

### How to Fix

Rename the permission to open with a verb from the use-case verb table with `litespec rename`, or declare the domain verb in the `vocabulary` of `litespec.project.json`, in `queryVerbs` when it opens only a query.

## Notes

### What the Rule Ignores

The rule does not run in test projects, where no permission metadata is generated. It stays silent when no `litespec.project.json` is in reach, or when the docs root it names cannot be resolved; the CLI owns that configuration error.

### Severity

The rule is an error whenever it fires, because the record is the only permission list and an undeclared verb leaves whether the permission only reads undecided. An `.editorconfig` entry for the rule id overrides it.
