# LS2041: Closed-Set Code Written as a String Literal

LS2041 reports a string literal used for the Code of a closed set: a comparison against Code, or a refusal Code defined with a literal. Callers branch on the typed case or compare a CodeValue constant, and a refusal carries its code from the synced refusal constant, so a renamed code fails the build instead of shipping a typo.

## Reference

### What the Rule Enforces

LS2041 enforces [Model Every Closed Set of Domain Values Without Enums](../../packs/dotnet/domain.md#model-every-closed-set-of-domain-values-without-enums) (`litespec/packs/dotnet/domain#model-every-closed-set-of-domain-values-without-enums`). It runs in every layer except Test. Its category is `LiteSpec.Layers`. Severity and enablement follow the [Analyzers overview](../README.md).

### What the Rule Reports

A `==` or `!=` comparison reports when one side is a string literal and the other side reads a `Code` property of string type declared on an abstract type: a closed set such as `ExpenseKind`, or a refusal base such as `DomainException`. An `Equals` call reports for the same pairing, both `code.Equals("...")` and `string.Equals(code, "...")`. A `Code` property on a `DomainException` subclass reports when its value is a string literal: an arrow body, a getter return, or an initializer. The diagnostic sits on the string literal, and its message names the type and the fix.

### Failing Example

```csharp
namespace Claimwick.Spending.Application.SubmitExpense;

internal sealed class SubmitExpenseCommandHandler
{
    public bool Handle(Expense expense)
    {
        return expense.Kind.Code == "standard";
    }
}
```

with `ExpenseKind` declared as an abstract record with a `Code` property and a `StandardExpenseKind` sealed case. The same comparison with `!=`, or an `Equals` call with the literal, reports the same way.

```csharp
namespace Claimwick.Spending.Domain.Expenses.Exceptions;

internal sealed class ExpenseReceiptMissingException : DomainException
{
    public ExpenseReceiptMissingException()
        : base("An expense above the receipt threshold carries no receipt.")
    {
    }

    public override string Code => "spending.receipt-missing";
}
```

### Passing Example

```csharp
namespace Claimwick.Spending.Application.SubmitExpense;

internal sealed class SubmitExpenseCommandHandler
{
    public bool Handle(Expense expense)
    {
        return expense.Kind is StandardExpenseKind;
    }
}
```

The check branches on the sealed case, so a new case gets its own arm instead of falling through a literal. In a queryable expression the driver cannot send a case, so the comparison reads the `CodeValue` constant on the sealed case:

```csharp
return expense.Kind.Code == StandardExpenseKind.CodeValue;
```

```csharp
namespace Claimwick.Spending.Domain.Expenses.Exceptions;

internal sealed class ExpenseReceiptMissingException : DomainException
{
    public ExpenseReceiptMissingException()
        : base("An expense above the receipt threshold carries no receipt.")
    {
    }

    public override string Code => SpendingRefusalCodes.ReceiptMissing;
}
```

The refusal carries the synced constant the generator writes from the refusal record.

### How to Fix

Branch on the sealed case with `is` or `switch`. In a queryable expression compare the `CodeValue` constant on the sealed case, which the driver can send. Carry a refusal code from the synced `{Module}RefusalCodes` constant, which the generator writes from the refusal the rule names.

## Notes

### What the Rule Ignores

A comparison with no string literal never reports, including a comparison against a `CodeValue` constant or another `Code`. A `Code` declared on a concrete type never reports: only an abstract base marks a closed family, so a `Code` on a struct such as `CountryKey` stays quiet. A `Code` built with interpolation or concatenation never reports: only a direct literal does. The rule does not run in Test files, or in a file the layer rules cannot place.
