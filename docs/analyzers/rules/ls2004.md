# LS2004: Command Handler Writes Through a Document Session

LS2004 reports a command handler that writes through a document session or database context. A command handler runs the state change and reaches stored data through a repository, which guards the aggregate it stages. Writing through a document session or database context bypasses that boundary.

## Reference

### What the Rule Enforces

LS2004 enforces [Stage aggregate writes through repositories](../../backend/dotnet/persistence.md#stage-aggregate-writes-through-repositories) (`litespec/backend/dotnet/persistence#stage-aggregate-writes-through-repositories`). It runs in Application, Infrastructure, and Worker. Its category is `LiteSpec.Layers`. Severity and enablement follow the [Analyzers overview](../README.md).

### What the Rule Reports

A command handler is a class whose name ends in `CommandHandler` or that implements `ICommandHandler`. The rule reports one that holds `IDocumentSession`, `DbContext`, or a `DbContext` subclass in a field, property, constructor parameter, or local, or that calls a member through such a receiver. In a declaration the diagnostic sits on the type; in a call it sits on the invoked member name.

### Failing Example

```csharp
internal sealed class PlaceOrderCommandHandler
{
    private readonly IDocumentSession _session = null!;
}
```

### Passing Example

```csharp
internal sealed class PlaceOrderCommandHandler(IOrderRepository orderRepository)
{
    public void Handle(PlaceOrderCommand command)
    {
        var order = Order.Create(command.Quantity);
        orderRepository.Store(order);
    }
}
```

### How to Fix

Reach persistence only through a Domain repository, taken as a constructor parameter of the handler.

## Notes

### What the Rule Ignores

Handlers that reach persistence only through a Domain repository never report, and query handlers are out of scope entirely. The rule does not run in Domain or WebApi.
