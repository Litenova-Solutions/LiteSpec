# LS2019: Use Case Names a Type of Another Use Case

LS2019 reports a use case folder that names a type declared in another use case folder. Each use case folder is a slice that changes for its own reasons, so each slice names only its own types plus the layer folders; a reference from one slice to another couples work that changes for different reasons.

## Reference

### What the Rule Enforces

LS2019 enforces [Keep Use Case Folders Isolated](../../backend/dotnet/architecture.md#keep-use-case-folders-isolated) (`litespec/backend/dotnet/architecture#keep-use-case-folders-isolated`). It runs in every layer except Test. Its category is `LiteSpec.Layers`. Severity and enablement follow the [Analyzers overview](../README.md).

### What the Rule Reports

A name in a use case folder under `UseCases/`, in its `Application/`, `WebApi/`, `Infrastructure/`, or later layer folder, reports when it resolves to a type declared in another use case folder. The message and the result of another use case are no exception: a reaction or job sits in the folder of the use case it runs, so it sends that use case's message from there. The diagnostic sits on the name, and its message names the type and the folder that owns it.

### Failing Example

```csharp
namespace Claimwick.Spending.Expenses.UseCases.SubmitExpense;

internal sealed class SubmitExpenseCommandHandler
{
    public void Handle() => ApproveExpensePolicy.ForExpense();
}
```

with the file in `Spending/Expenses/UseCases/SubmitExpense/Application/` and `ApproveExpensePolicy` declared in `Spending/Expenses/UseCases/ApproveExpense/Application/`.

### Passing Example

```csharp
namespace Claimwick.Spending.Expenses.UseCases.SubmitExpense;

internal sealed class SubmitExpenseCommandHandler
{
    private readonly IExpensePolicy _policy;

    public SubmitExpenseCommandHandler(IExpensePolicy policy)
    {
        _policy = policy;
    }
}
```

with the file in `Spending/Expenses/UseCases/SubmitExpense/Application/` and `IExpensePolicy` declared in `Spending/Expenses/Application/`, the folder of the aggregate that every use case names.

### How to Fix

Lift the shared type to the aggregate, module, or Kernel folder that holds every consumer naming it. A type two use cases name belongs beside their aggregate, not inside either slice. Kernel values are the exception: money, typed identifiers, dates, and closed sets the Kernel owns are referenced directly from any slice, never copied into one. A reaction that runs a use case goes in that use case's `Application/` folder, so it names that use case's message without crossing a slice.

## Notes

### What the Rule Ignores

A name in a Test file, or in a file the layer rules cannot place, never reports. The rule leaves alone a type in the same folder or in a layer folder, and a name that resolves to no project source file. It exempts no use case message or result by name: a reaction that sends a command and reads its result sits in the folder of the use case it runs, so the names it uses are its own.
