# LS1001: Domain References an Outer-Layer Concern

LS1001 reports code in Domain naming a persistence, web, messaging, or logging type, which ties business rules to infrastructure they cannot test on their own.

## Reference

### What the Rule Enforces

LS1001 enforces [Keep Domain free of outer-layer concerns](../../backend/dotnet/domain.md#keep-domain-free-of-outer-layer-concerns) (`litespec/backend/dotnet/domain#keep-domain-free-of-outer-layer-concerns`). It runs in Domain only. Its category is `LiteSpec.Domain`. Severity and enablement follow the [Analyzers overview](../README.md).

### What the Rule Reports

The rule checks every identifier and `using` name against the outer-layer namespace prefixes listed on the overview, and reports each one that resolves to them. The diagnostic sits on the identifier in code, and on the name in a `using` directive. Its message names the offending type and the namespace it comes from.

### Failing Example

```csharp
using Microsoft.Extensions.Logging;

namespace Shop.Orders.Domain;

public sealed class Order
{
}
```

### Passing Example

```csharp
using System;
using System.Collections.Generic;

namespace Shop.Orders.Domain;

public sealed class Order
{
    public List<string> Tags { get; } = new();

    public DateTime PlacedAt { get; init; }
}
```

### How to Fix

Move the use out of Domain: depend on a Domain type or a base class library type instead, and adapt the outer-layer service in Application or Infrastructure.

## Notes

### What the Rule Ignores

Project types and base class library types such as `System`, `System.Collections.Generic`, and `System.Linq` never report, and neither do `var` or documentation comments. A namespace that merely shares a prefix, such as `MartenStore`, does not match. In a member access such as `session.Store(session)`, the diagnostic lands on the member name rather than the qualifier. The rule does not run outside Domain.
