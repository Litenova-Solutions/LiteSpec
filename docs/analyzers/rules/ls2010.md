# LS2010: Repository Variable Not Named After Its Interface

LS2010 reports a repository parameter, field, or local whose name does not follow its interface. A repository variable follows the name of its interface, so a reader can tell which aggregate the variable stages without looking up its type.

## Reference

### What the Rule Enforces

LS2010 enforces [Name repository variables after their interface](../../workspace/naming.md#name-repository-variables-after-their-interface) (`litespec/workspace/naming#name-repository-variables-after-their-interface`). It runs in Application, Infrastructure, and Worker. Its category is `LiteSpec.Layers`. Severity and enablement follow the [Analyzers overview](../README.md).

### What the Rule Reports

A parameter, field, or local typed as an interface named `I{Name}Repository` reports when its name is not `{name}Repository`, the interface name without its `I` prefix starting in lower case. A field may carry one leading underscore. The diagnostic sits on the variable name, and its message names the variable, the interface, and the expected name.

### Failing Example

```csharp
internal sealed class ApproveExpenseCommandHandler(IExpenseRepository expenses)
{
}
```

### Passing Example

```csharp
internal sealed class ApproveExpenseCommandHandler(IExpenseRepository expenseRepository)
{
    private readonly IExpenseRepository _expenseRepository = expenseRepository;
}
```

### How to Fix

Take the variable name from its interface: drop the `I` prefix, start in lower case, and end in `Repository`, such as `expenseRepository` for `IExpenseRepository`.

## Notes

### What the Rule Ignores

A variable typed as anything but an interface named `I{Name}Repository` never reports, including other interfaces and concrete classes. The rule does not run in Domain or WebApi.
