# LS3002: CancellationToken Is Not the Last Parameter

LS3002 reports a cancellation token parameter that is misplaced or misnamed. An async method that takes a token puts it last and under one name, so callers pass it the same way everywhere; a token in the wrong position is easy to pass wrongly, and a token under another name hides what it is at the call site.

## Reference

### What the Rule Enforces

LS3002 enforces [Put the cancellation token last](../../backend/dotnet/naming.md#put-the-cancellation-token-last) (`litespec/backend/dotnet/naming#put-the-cancellation-token-last`). It runs in every production project. Its category is `LiteSpec.Style`. Severity and enablement follow the [Analyzers overview](../README.md).

### What the Rule Reports

A `CancellationToken` parameter reports when it is not the last parameter, or when it is not named exactly `cancellationToken`. The token may sit second to last when the last parameter is a `params` array. The diagnostic sits on the token parameter.

### Failing Example

```csharp
public Task LoadAsync(CancellationToken cancellationToken, string name) => Task.CompletedTask;
```

### Passing Example

```csharp
public Task SaveAsync(string name, CancellationToken cancellationToken) => Task.CompletedTask;
```

### How to Fix

Put the token last, or before a trailing `params` array, and name it `cancellationToken`.

## Notes

### What the Rule Ignores

A method without a token never reports. Neither does an override, an explicit interface implementation, or an implementation of a member from an outside interface. In an endpoint handler, where the framework binds by type, the rule checks only the token name. It accepts `stoppingToken` in a hosted service, where the token threads host shutdown from `ExecuteAsync`. The rule does not run outside the production layers.
