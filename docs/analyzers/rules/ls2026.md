# LS2026: Model Duplicated in Two Use Case Folders

LS2026 reports two use case folders of one module that declare a record with the same name and the same members. A shape two use cases need is declared once beside the aggregate they share, or referenced from the Kernel when it is a shared value; a copy in each folder drifts.

## Reference

### What the Rule Enforces

LS2026 enforces [Keep Use Case Folders Isolated](../../backend/dotnet/architecture.md#keep-use-case-folders-isolated) (`litespec/backend/dotnet/architecture#keep-use-case-folders-isolated`). It runs in every production layer and decides at the end of compilation, as the [Analyzers overview](../README.md) describes. Its category is `LiteSpec.Layers`. Severity and enablement follow the [Analyzers overview](../README.md).

### What the Rule Reports

Two records report when they share one module, one simple name, and the same instance properties and fields with the same types, but sit in different use case folders. The first declaration in file order keeps the model; each later copy reports. The diagnostic sits on the record name, and its message names both use cases, adding the shared value to reference when one matches.

### Failing Example

```csharp
namespace Claimwick.Spending.WebApi.Expenses.ApproveExpense;

internal sealed record MoneyModel(decimal Amount, string Currency);
```

with the same record declared again in `Spending/WebApi/Expenses/ReimburseExpense/`. The later copy reports, naming the other use case and the shared `Money` value.

### Passing Example

```csharp
namespace Claimwick.Spending.WebApi.Expenses.ApproveExpense;

internal sealed class ApproveExpenseEndpoint
{
    public ApproveExpenseResponse Get(Money budget)
    {
        return new ApproveExpenseResponse(budget);
    }
}
```

Both use cases reference the shared `Money` value instead of declaring their own.

### How to Fix

Delete the copies and reference the shared value, or declare the shape once beside the aggregate both use cases name. Two records that only share a name but differ in members are not copies and never report.

## Notes

### What the Rule Ignores

Two records with different members, in different modules, or in the same use case folder never report. A record outside every use case folder never reports, and neither does a class that is not a record. The rule does not run outside the production layers.
