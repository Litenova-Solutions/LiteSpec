# LS2009: Result Part Not Named After Its Result

A use-case result reaches its part types through its properties, and each part name starts with the result name, so a reader can tell which result the part belongs to. LS2009 reports a part that does not.

## Reference

### What the Rule Enforces

LS2009 enforces [Name result parts after their result](../../workspace/naming.md#name-result-parts-after-their-result) (`litespec/workspace/naming#name-result-parts-after-their-result`). It runs in Application, Infrastructure, and Worker. Its category is `LiteSpec.Layers`. Severity and enablement follow the [Analyzers overview](../README.md).

### What the Rule Reports

A type declared in the same namespace as a `{UseCase}QueryResult` or `{UseCase}CommandResult` type reports when the result reaches it through a public property, directly or through another part, including as a collection element, while its name does not start with the result name. A helper the handler uses that the result does not reach, such as a page reader or a cursor, is not a part, so the rule ignores it. The diagnostic sits on the type name, and its message names the part and the result it belongs to.

### Failing Example

```csharp
public sealed record ReadLoanQueryResult(int LoanId, LoanHoldItem[] Holds);

public sealed record LoanHoldItem(int HoldId);
```

### Passing Example

```csharp
public sealed record ReadLoanQueryResult(int LoanId, ReadLoanQueryResultHold[] Holds);

public sealed record ReadLoanQueryResultHold(int HoldId);
```

### How to Fix

Name the part `{UseCase}QueryResult{Part}` or `{UseCase}CommandResult{Part}`, starting with the full result name.

## Notes

### What the Rule Ignores

The result itself never reports, and neither does a type the result does not reach (the message, handler, validator, definition, or a helper), a nested type, or a type declared where no result is declared. The rule does not run in Domain or WebApi.
