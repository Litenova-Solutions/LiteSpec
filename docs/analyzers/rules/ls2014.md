# LS2014: Command Handler Finds or Creates

One command runs one outcome path. A handler that finds a record and creates it only where the find came back empty hides two use cases, find and create, behind one name. LS2014 reports the handler that does both in one method.

## Reference

### What the Rule Enforces

LS2014 enforces [Implement one outcome path per command](../../backend/application.md#implement-one-outcome-path-per-command) (`litespec/backend/application#implement-one-outcome-path-per-command`). It runs in Application, Infrastructure, and Worker. Its category is `LiteSpec.Layers`. Severity and enablement follow the [Analyzers overview](../README.md).

### What the Rule Reports

The rule reports a command handler, which is a class whose name ends in `CommandHandler` or that implements `ICommandHandler`, with one method that calls a repository method whose name starts in `Find` and creates the found type, through a static method or a constructor, only where the find came back empty, ignoring `Task` and nullability. A creation runs where the find came back empty when it sits on the null side of a test of the found value, after a branch that returns or throws when the value was found, or on the null side of `??` or `??=`. For a constructor the diagnostic sits on the created type; for a static factory it sits on the invoked member name. Its message names the handler and the created type.

### Failing Example

```csharp
internal sealed class RegisterReaderCommandHandler(IReaderRepository readerRepository)
{
    public void Handle(RegisterReaderCommand command)
    {
        var reader = readerRepository.FindByCard(command.CardId)
            ?? Reader.Register(command.CardId);
        readerRepository.Store(reader);
    }
}
```

### Passing Example

```csharp
internal sealed class RegisterReaderCommandHandler(IReaderRepository readerRepository)
{
    public void Handle(RegisterReaderCommand command)
    {
        var reader = Reader.Register(command.CardId);
        readerRepository.Store(reader);
    }
}
```

### How to Fix

Split the flow into two use cases, with the boundary that owns the flow running a query first and then sending the command that fits. When the create loses a race, it refuses with its conflict, and the owner sends the other command. Where the record is usually present, the boundary sends the command first and, on the record's not-found refusal, sends the create and then the command again. Keep that sequence in one helper beside the command mediator, such as `commands.SendToRecord(command).CreatingItOn<ReaderNotFoundException>(register, cancellationToken)`, rather than repeating it in each endpoint.

## Notes

### What the Rule Ignores

A handler that only finds never reports, and neither does one that only creates, a creation of another type than the found one, or a creation that runs whether or not the find came back empty, such as a fine statement that reads the reader's previous statement to carry its balance. The rule leaves alone a creation after the handler refuses a missing record, a creation inside a switch arm keyed on another value than the found one, and a find and a creation in different methods. Query handlers never report. The rule does not run in Domain or WebApi.
