# LS5014: Development Shortcut Compiled Without DEBUG

LS5014 reports a type tagged as a development shortcut when its declaration compiles into a build that does not define the `DEBUG` symbol. A shortcut is code that makes local development faster by weakening a production behavior, so it must stay out of release builds. The rule catches the reference that a release build would carry.

## Reference

### What the Rule Enforces

LS5014 enforces [Keep Development Shortcuts Out of Release Builds](../../quality/development.md#keep-development-shortcuts-out-of-release-builds) (`litespec/quality/development#keep-development-shortcuts-out-of-release-builds`). It runs in every layer the rules place, including test projects. Its category is `LiteSpec.Traceability`.

### What the Rule Reports

A class, struct, record or interface whose `///` documentation carries a `<development-shortcut>` tag reports when a declaration of it compiles without `DEBUG`. The diagnostic sits on the type name.

The tag takes the reason the shortcut exists. A tag whose reason is empty or only whitespace reports in a build that defines `DEBUG`. A type that lacks both `DEBUG` and a reason reports once, with the `DEBUG` message, because the shortcut reaching a release build matters more than the missing reason.

### Failing Example

The sign-in shortcut below sits in a project that the host references in every build, so a `Release` compilation has no `DEBUG` symbol:

```csharp
/// <development-shortcut>Sign in as Ava locally</development-shortcut>
public sealed class DevelopmentSignIn
{
}
```

LS5014 reports `DevelopmentSignIn` in the `Release` build.

### Passing Example

The same type passes when its project is referenced only in Debug builds and its registration sits behind `#if DEBUG`:

```csharp
/// <development-shortcut>Sign in as Ava locally</development-shortcut>
public sealed class DevelopmentSignIn
{
}
```

```csharp
var builder = WebApplication.CreateBuilder(args);

#if DEBUG
builder.Services.AddDevelopmentSignIn();
#endif
```

The type itself stays outside `#if DEBUG`. A region the compiler drops is not part of the compilation, so the rule could not see the type in a release build.

### How to Fix

Reference the project only in Debug builds, with `Condition="'$(Configuration)' == 'Debug'"` on its `ProjectReference`, and register it behind `#if DEBUG`. The [.NET workspace page](../../backend/dotnet/workspace.md#exclude-development-shortcuts-from-release-builds) states the full binding.

For a tag with an empty reason, write in the tag why the shortcut exists. For a type that is not a shortcut, remove the tag.

## Notes

### What the Rule Ignores

The rule reads the tag from `///` comment text, so it works whether or not the project generates a documentation file. A `//` comment that names the tag is not a tag.

The rule checks the `DEBUG` symbol of the compilation the declaration belongs to. It does not read the project file, so a `Condition` on a `ProjectReference` is checked by review against the stack page, not by this rule.

The rule reads no records, so it runs without `.litespec/project.yaml`. It stays silent for files the rules cannot place, and it does not analyze generated code.

### Severity

The rule is an error whenever it fires. An `.editorconfig` entry for the rule id overrides the severity.
