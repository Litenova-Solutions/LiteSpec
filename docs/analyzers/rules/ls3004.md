# LS3004: Concrete Class Is Not Sealed

A class designed for extension says so through a virtual or protected member. A concrete class with no derived type and no such member reads as a finished leaf, and leaving it unsealed invites subclasses the author never meant. LS3004 reports the unsealed leaf.

## Reference

### What the Rule Enforces

LS3004 enforces [Keep implementation style consistent](../../backend/dotnet/naming.md#keep-implementation-style-consistent) (`litespec/backend/dotnet/naming#keep-implementation-style-consistent`). It runs in every production project. Its category is `LiteSpec.Style`. Severity and enablement follow the [Analyzers overview](../README.md). It decides at the end of compilation, as the [Analyzers overview](../README.md) describes.

### What the Rule Reports

A concrete class declared in source reports when nothing derives from it and it is not sealed. The diagnostic sits on the class name.

### Failing Example

```csharp
public class Order { }
```

### Passing Example

```csharp
public sealed class Order { }
```

### How to Fix

Seal the leaf class, or add the virtual or protected member that shows the class is designed for extension.

## Notes

### What the Rule Ignores

Records, static classes, abstract classes, sealed classes, and the `Program` composition marker never report. A base with a derived class passes, as does a class designed for extension through a virtual member, an unsealed override, or a protected member. The rule does not run outside the production layers.
