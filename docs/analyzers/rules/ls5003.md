# LS5003: Code Element Carries the Wrong Number of Marks

LS5003 reports a code element carrying more or fewer marks than its kind takes. Each kind of code element takes a fixed number of marks: most kinds take exactly one, naming the one record the element serves. An extra mark points the element at a record it does not serve.

## Reference

### What the Rule Enforces

LS5003 enforces [Point Code and Tests up to Records](../../core/system.md#point-code-and-tests-up-to-records) (`litespec/core/system#point-code-and-tests-up-to-records`). It runs in every layer, on every marked code element and test. Its category is `LiteSpec.Traceability`.

### What the Rule Reports

A code element whose mark count differs from what its kind takes reports: a handler, event handler, job, endpoint, aggregate root, aggregate method, domain event, rule exception, or domain service carrying more than one mark, or an element naming one record twice, which counts as two marks.

Each aggregate root method that changes state performs the act of exactly one use case, following [Give Each Use Case Its Own Act](../../backend/domain.md#give-each-use-case-its-own-act). The marks table on the [model page](../../core/model.md#marks) states the count each kind takes. The diagnostic sits on the type or method name.

### Failing Example

```csharp
/// <implements>use-case/spending.submit-expense</implements>
/// <implements>use-case/spending.approve-expense</implements>
internal sealed class SubmitExpenseCommandHandler(...)
    : ICommandHandler<SubmitExpenseCommand, SubmitExpenseCommandResult>
{
    // Loads the expense, submits it, stages it, and returns the result.
}
```

A root method shared by two use cases reports as well:

```csharp
/// <implements>aggregate/spending.expense</implements>
public sealed class Expense : AggregateRoot<ExpenseState>
{
    /// <implements>use-case/spending.approve-expense</implements>
    /// <implements>use-case/spending.approve-expense-on-behalf</implements>
    public void Approve(Guid approverId, DateTimeOffset decidedAt)
    {
        // Checks the submitter, replaces the state, and records the approval.
    }
}
```

### Passing Example

```csharp
/// <implements>use-case/spending.submit-expense</implements>
internal sealed class SubmitExpenseCommandHandler(...)
    : ICommandHandler<SubmitExpenseCommand, SubmitExpenseCommandResult>
{
    // Loads the expense, submits it, stages it, and returns the result.
}
```

One method per act with a private shared helper passes:

```csharp
/// <implements>aggregate/spending.expense</implements>
public sealed class Expense : AggregateRoot<ExpenseState>
{
    /// <implements>use-case/spending.approve-expense</implements>
    public void Approve(Guid approverId, DateTimeOffset decidedAt) => RecordApproval(approverId, decidedAt);

    /// <implements>use-case/spending.approve-expense-on-behalf</implements>
    public void ApproveOnBehalf(Guid approverId, DateTimeOffset decidedAt) => RecordApproval(approverId, decidedAt);

    private void RecordApproval(Guid approverId, DateTimeOffset decidedAt)
    {
        // Checks the submitter, replaces the state, and records the approval.
    }
}
```

### How to Fix

Remove the mark the kind does not take, so the element carries exactly the marks its kind takes. When one method serves two use cases, split it into one marked method per act with a private shared helper, as the passing example shows.

## Notes

### What the Rule Ignores

An element with no mark never reports; `litespec model check` owns that finding. An element carrying the marks its kind takes passes, including a port, adapter, or test carrying several marks.

The rule stays silent when no `.litespec/project.yaml` is in reach, or when the docs root it names cannot be resolved; the CLI owns that configuration error.

### Severity

The rule reports an error. A finding that a live waiver covers stays silent, and an `.editorconfig` entry for the rule id overrides the computed severity.
