# LS2029: File Names a Contract Type Outside Its Layer

LS2029 reports a module file that names another module's public query, public command or result outside its provider adapter, and a Platform file that names a module identifier. A consumer reaches another module through one port per provider: the adapter in `Infrastructure/{Provider}/` sends the provider's public queries and public commands and maps their results, so a query or command named anywhere else couples the caller to a call the port never declared. The Platform speaks the tenant and the actor, never a business identifier the modules own.

## Reference

### What the Rule Enforces

LS2029 enforces [Follow Layer Direction in Every File](../../backend/dotnet/architecture.md#follow-layer-direction-in-every-file) (`litespec/backend/dotnet/architecture#follow-layer-direction-in-every-file`). It runs in every layer except Test, including Platform files. Its category is `LiteSpec.Layers`. Severity and enablement follow the [Analyzers overview](../README.md).

### What the Rule Reports

A name in a module file outside an `Infrastructure/{Provider}/` adapter folder reports when it resolves to a public query, public command or result of another module: a type in a `{UseCase}/` folder below an aggregate folder of that module's Contracts project, or a module-level public query or public command sitting in its own Contracts folder. A type in an `Events/` folder below an aggregate folder is a fact, never a public query, public command or result. Naming another module's identifiers and facts from the same file stays allowed. A name in a Platform file reports when it resolves to a module identifier: a type ending in `Id` declared in a module. The diagnostic sits on the name, and its message names the file's layer, the type, and why the layer may not name it: for a query or command, the provider module and its adapter folder; for an identifier, that the Platform names no business identifier.

### Failing Example

```csharp
namespace Claimwick.Reading.Application.BorrowBook;

internal sealed class BorrowBookQueryHandler
{
    internal void Handle(ReadBookQuery query)
    {
    }
}
```

with `ReadBookQuery` declared in the books module `Contracts/Books/ReadBook/` folder.

A handler naming another module's public command reports the same way:

```csharp
namespace Claimwick.Reading.Application.BorrowBook;

internal sealed class BorrowBookCommandHandler
{
    internal void Handle(LendBookCommand command)
    {
    }
}
```

with `LendBookCommand` declared in the books module `Contracts/Books/LendBook/` folder.

A Platform file reports the same way:

```csharp
namespace Claimwick.Platform.Access;

internal sealed class ActorScope
{
    internal void Attach(BookId book)
    {
    }
}
```

with `BookId` declared in the books module Contracts.

### Passing Example

```csharp
namespace Claimwick.Reading.Infrastructure.Books;

internal sealed class BooksAdapter
{
    internal ReadBookQuery Query() => new();
}
```

with `ReadBookQuery` declared in the books module `Contracts/Books/ReadBook/` folder. The adapter is the only code that sends another module's public queries and public commands, so it is the only code that names the query, command and result types.

### How to Fix

Name the provider's public query or public command only from the adapter in `Infrastructure/{Provider}/`, which sends it and maps its result onto the consumer's own types, and reach the provider from handlers through the consumer's port to that module. Move a business identifier the Platform reads into the module that owns it, and convert at the module edge: the Platform speaks the tenant and the actor.

## Notes

### What the Rule Ignores

A name in a Test file never reports. The rule leaves alone a name in an adapter folder, a name resolving to the file's own module, a module identifier or fact named from a module file, a Kernel value or the Platform's own type named from a Platform file, and a name that resolves to no project source file. A file outside every module, such as a host file, never reports.
