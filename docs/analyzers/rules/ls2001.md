# LS2001: Implementation Type Is Not Internal Sealed

Callers should reach behavior through its interface, not through the class that implements it. A handler, validator, endpoint, or other implementation type that callers can see invites them to depend on it directly. LS2001 reports an implementation type in the Application, Infrastructure, WebApi, and Worker layers that is not `internal sealed`.

## Reference

### What the Rule Enforces

LS2001 enforces [Keep implementation types internal](../../backend/dotnet/architecture.md#keep-implementation-types-internal) (`litespec/backend/dotnet/architecture#keep-implementation-types-internal`). It runs in Application, Infrastructure, WebApi, and Worker. Its category is `LiteSpec.Layers`. Severity and enablement follow the [Analyzers overview](../README.md).

### What the Rule Reports

A class whose name ends in `Handler`, `PreHandler`, `PostHandler`, `Validator`, `Endpoint`, `Definition`, `Repository`, `Configuration`, or `Projection`, or that implements `IEndpoint`, `ICommandHandler`, `IQueryHandler`, `IEventHandler`, or `IValidator`, reports unless it is both sealed and non-public. The diagnostic sits on the type name.

### Failing Example

```csharp
namespace Shop.Orders.UseCases.PlaceOrder;

public sealed class PlaceOrderCommandHandler { }
```

### Passing Example

```csharp
namespace Shop.Orders.UseCases.PlaceOrder;

internal sealed class PlaceOrderCommandHandler { }
```

### How to Fix

Declare the implementation type `internal sealed`.

## Notes

### What the Rule Ignores

An abstract class never reports, and neither does a class without an implementation name such as `OrderService`. The rule does not run in Domain.
