# LS5001: Code Element Carries No Mark

No tool can tell which record a code element implements unless the element says so. A code element of a recognized kind names the record it serves in a mark, and the analyzers check the marks at compile time. LS5001 reports a code element of a recognized kind that carries no mark.

## Reference

### What the Rule Enforces

LS5001 enforces [Point Code and Tests up to Records](../../core/system.md#point-code-and-tests-up-to-records) (`litespec/core/system#point-code-and-tests-up-to-records`) and [Point Every Technical Class up to Its Record or Choice](../../core/system.md#point-every-technical-class-up-to-its-record-or-choice) (`litespec/core/system#point-every-technical-class-up-to-its-record-or-choice`). It runs in every layer, checking the kinds that layer holds: Domain checks aggregate roots, state-changing methods, domain events, rule exceptions, and domain services; Application checks command and query handlers, event handlers, jobs, ports, and technical classes; Infrastructure checks adapters, jobs, and technical classes; WebApi checks endpoints and technical classes; Worker checks jobs and technical classes; and test projects check tests. Its category is `LiteSpec.Traceability`.

### What the Rule Reports

The rule reports a code element of a recognized kind that carries no mark. It recognizes each kind from the code:

- A handler is a class implementing an interface named `ICommandHandler` or `IQueryHandler`.
- An event handler is a class implementing an interface named `IEventHandler` or `IDomainEventReaction`.
- A job is a class deriving from a class named `BackgroundService`, or implementing an interface named `IHostedService` and named `*Job` or `*Worker`.
- An aggregate root is a class deriving from a class named `AggregateRoot` with one type argument.
- An aggregate method is a public instance or static method on an aggregate root that raises a domain event.
- A domain event is a type implementing an interface named `IDomainEvent`.
- A rule exception is a non-abstract class deriving from a class named `DomainException`.
- An endpoint is a class implementing an interface named `IEndpoint`, or named `*Endpoint` in WebApi.
- An adapter is a class implementing a marked port.
- A technical class is a top-level class in Application, Infrastructure, or WebApi that takes no other kind and declares an ordinary method.
- A test is a method carrying a test attribute.

The marks table on the [model page](../../core/model.md#marks) states which record each kind names: a technical class carries an `implements` mark naming the Behavior record it serves, or a `follows` mark naming the provision, decision, or waiver that shapes it. The diagnostic sits on the type or method name.

### Failing Example

```csharp
internal sealed class SubmitExpenseCommandHandler(...)
    : ICommandHandler<SubmitExpenseCommand, SubmitExpenseCommandResult>
{
    // Loads the expense, submits it, stages it, and returns the result.
}
```

A technical class with no mark reports as well:

```csharp
internal sealed class SubmitExpenseValidator
{
    public Task ValidateAsync(CancellationToken cancellationToken) => Task.CompletedTask;
}
```

### Passing Example

```csharp
/// <implements>use-case/spending.submit-expense</implements>
internal sealed class SubmitExpenseCommandHandler(...)
    : ICommandHandler<SubmitExpenseCommand, SubmitExpenseCommandResult>
{
    // Loads the expense, submits it, stages it, and returns the result.
}
```

The same validator with its `implements` mark passes:

```csharp
/// <implements>use-case/spending.submit-expense</implements>
internal sealed class SubmitExpenseValidator
{
    public Task ValidateAsync(CancellationToken cancellationToken) => Task.CompletedTask;
}
```

A technical class with a `follows` mark passes as well:

```csharp
/// <follows>litespec/backend/persistence#commit-each-command-pipeline-once</follows>
internal sealed class CommitStep
{
    public Task CommitAsync(CancellationToken cancellationToken) => Task.CompletedTask;
}
```

### How to Fix

Add the mark that names the record the element serves, in the style the project declares. A code fix adds the missing mark, offering one action per candidate record titled with the record title, with no Fix All. For a technical class the fix offers the use-case records marked by handlers in the same folder. When no sibling handler marks a use case, name the Behavior record it serves or the provision, decision, or waiver that shapes it.

## Notes

### What the Rule Ignores

A port or a domain service is recognized only by its mark, so an unmarked one never reports; an unmarked port is found from the top instead, through its external system. A state-changing method that raises no event is likewise recognized only once it carries a mark. A minimal-API route with no endpoint type never reports. A record, interface, nested type, generated class, migration, or class with no ordinary method is never a technical class, and types in test projects are never domain events, jobs, or endpoints. The rule reads C# only; frontend `litespec` constants are checked by `litespec model check`. The rule stays silent when no `.litespec/project.yaml` is in reach, or when the docs root it names cannot be resolved; the CLI owns that configuration error.

### Severity

The finding names no record, so it reports as an error. A finding that a live waiver covers stays silent, and an `.editorconfig` entry for the rule id overrides the computed severity.
