# LS2036: Production Code Reads the Clock Directly

LS2036 reports a static clock read outside Domain. One message answers to one time: handlers read the pipeline timestamp, and Infrastructure reads an injected clock. A direct read stamps a second moment, sometimes with an outside call in between.

## Reference

### What the Rule Enforces

LS2036 enforces [Read Time from the Scoped Clock](../../core/backend-application.md#read-time-from-the-scoped-clock) (`litespec/core/backend-application#read-time-from-the-scoped-clock`). It runs in Application, Ports, Infrastructure, WebApi, and Worker. Its category is `LiteSpec.Layers`. Severity and enablement follow the [Analyzers overview](../README.md).

### What the Rule Reports

The rule reports reads of `DateTime.Now`, `DateTime.UtcNow`, `DateTime.Today`, `DateTimeOffset.Now`, and `DateTimeOffset.UtcNow`. The diagnostic sits on the member name, and its message names the read. Domain stays under LS1009, which also refuses randomness and new identifiers; those stay legal outside Domain, where creating version 7 identifiers is the documented fix, so the clock reads outside Domain get their own rule.

### Failing Example

```csharp
public DateTime Stamp()
{
    return DateTime.UtcNow;
}
```

### Passing Example

```csharp
public DateTime Stamp(ApproveExpenseCommand command)
{
    return command.HandledAt;
}
```

### How to Fix

Read the pipeline timestamp from the message in handlers, and inject a clock such as `TimeProvider` where Infrastructure needs the current time.

## Notes

### What the Rule Ignores

A read in a type carrying a `development-shortcut` tag never reports, and that tag is the only exemption: the tag sits on the type, as the workspace provision requires. Instance calls on an injected clock such as `clock.GetUtcNow()` never report, and neither do `TimeProvider.System`, randomness, new identifiers, or names inside `nameof`. The rule does not run in Domain or Test.
