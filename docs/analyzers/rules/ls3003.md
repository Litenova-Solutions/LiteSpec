# LS3003: File Does Not Match Its Primary Type

LS3003 reports a C# file whose name does not match the type it holds. A reader finds a type by its file name, so a mismatch sends every reader searching somewhere unexpected.

## Reference

### What the Rule Enforces

LS3003 enforces [Match C# files and primary types](../../backend/dotnet/naming.md#match-c-files-and-primary-types) (`litespec/backend/dotnet/naming#match-c-files-and-primary-types`). It runs in every production project. Its category is `LiteSpec.Style`. Severity and enablement follow the [Analyzers overview](../README.md).

### What the Rule Reports

A C# file reports when its single top-level type has a different name. When a file holds several top-level types, every type after the first reports.

A dotted file name such as `Order.Validation.cs` matches the part before the first dot. Generic arity is ignored, and partial declarations of the same type count once. Only types directly in the compilation unit or a namespace count; nested types never do. The diagnostic sits on the type name.

### Failing Example

In a file named `Order.cs`, this type reports:

```csharp
namespace Shop.Domain.Orders;

public sealed class Customer { }
```

### Passing Example

In a file named `Order.cs`, this type passes:

```csharp
namespace Shop.Domain.Orders;

public sealed class Order { }
```

### How to Fix

Rename the file after its one primary top-level type, or split the file so each top-level type gets its own file.

## Notes

### What the Rule Ignores

A file with no top-level types never reports. Nested private types never count, and neither do file-scoped types, so a class keeps its private shapes beside it. The rule does not run outside the production layers.
