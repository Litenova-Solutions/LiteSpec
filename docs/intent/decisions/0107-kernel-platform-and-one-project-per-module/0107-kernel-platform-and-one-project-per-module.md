# Kernel, Platform, and One Project per Module

A module is a business capability, and it is complete in one project. This decision separates the business values every module speaks into the Kernel, the technical capabilities into the Platform, and each module into its own project, with the four onion layer folders at the top of each module.

## Context

The two-project layout held business values and technical wiring in one shared kernel: money and typed identifiers beside mediator wiring, authorization guards, the audit sink, and JSON converters. Nothing separated a type a domain model may use from a type only a host touches.

Module registration lived in a `Composition/` folder inside the modules project, because two hosts needed the same wiring. The folder sat among the business modules and reached module internals across the same assembly.

Infrastructure had two homes and a use case had none. A use case held `Application/` and `WebApi/` only, so an adapter belonging to one use case landed in `Application/`. Technical setup repeated per module.

Module boundaries held as analyzer rules only, because one assembly held every module. Use cases sat five levels deep under one aggregate, and a use case changing two aggregates had to pick one parent. Aggregate folders shared their name with the aggregate type, so sibling files resolved the bare name to the namespace.

The slice layout that replaced the two-project layout put one use case in one folder with its own `Application/`, `WebApi/`, and `Infrastructure/` folders. It read as unfamiliar to its own owner: a .NET reader opening a module expects the four layer folders at the top, and a layout readers recognize is worth more than keeping one use case in one folder.

## Options

LiteSpec compared 5 options for the backend layout. The table sets each option against the same two points: what it gains and what it costs.

| Option | Gains | Costs |
|:---|:---|:---|
| Separate the Kernel, the Platform, and one project per module with onion layer folders | Module boundaries hold by project reference and visibility. The four layer folders read at first glance to anyone who knows .NET, and one style holds across products. | A solution holds more projects, one use case spreads over up to two folders, and small products carry the same shape as large ones. |
| Slice folders with layers in each use case | One folder shows a use case whole, with its layers beside its handler. | The layout reads as unfamiliar to .NET readers, and a second organization grows beside the layer checks. |
| Aggregate-first folders | Each aggregate holds its domain and its use cases in one place. | A use case touching two aggregates needs a second parent, and a use case no aggregate owns fits nowhere. |
| Onion projects per module | The compiler enforces layer purity inside each module through project references. | Four projects per module multiply the solution, and every use case crosses project boundaries. |
| Ports and adapters folders | Hexagonal names state the seams between the application and its drivers. | The vocabulary is new to the checks, and the ports-and-adapters split differs from the four layers the standard enforces. |

## Decision

The Kernel holds the business values every module speaks with no dependency on any library. The Platform holds the technical capabilities with no business words and references no module.

Each module is one project with its entry type, `Contracts/`, `Domain/`, `Application/`, `Ports/`, `Infrastructure/`, and `WebApi/`. The layer folders stand at the top of the module: `Application/` and `WebApi/` each hold one plural aggregate folder with one folder per use case inside it, `Application/{Aggregates}/{UseCase}/` always and `WebApi/{Aggregates}/{UseCase}/` when the use case is reached over HTTP. A module-level use case drops the aggregate segment in each. Aggregates live under `Domain/` with one folder each in the plural, while the root type keeps its singular name. `Infrastructure/Persistence/` nests by aggregate as well, so every layer nests by aggregate, and the module options class lives in `Application/Settings/`. `Domain/` is absent when the module declares no aggregate, `WebApi/` when no use case is reached over HTTP, and `Ports/` when the module declares no port.

The plural keeps the aggregate type visible: a singular folder makes a namespace such as `...Application.Expense.SubmitExpense` in which the C# name lookup finds the namespace before the `Expense` type, so every handler naming its aggregate fails with CS0118, and the same smell exists in a singular `Domain/Expense/` holding the type `Expense`. One plural folder in every layer also lets a reader follow one name from the record to the screen, because the code mirrors the record tree.

Only `Contracts/` and the entry type are public, so the compiler refuses any other cross-module reference. Hosts compose modules through `AddModules`, and modules plug into platform capabilities by contributing data instead of copying platform code.

The record tree stays as it is, with aggregate folders in the plural and record ids in the singular. A use case record under `aggregates/{aggregates}/use-cases/{use-case}` maps to code at `Application/{Aggregates}/{UseCase}/` and, when reached over HTTP, `WebApi/{Aggregates}/{UseCase}/`, and an aggregate record maps to code at `Domain/{Aggregates}/`. A use case record under `use-cases/{use-case}` drops the aggregate segment in every layer. Code drops the typed container folders of the record tree (`aggregates/`, `use-cases/`, `rules/`, `domain-events/`, `module-events/`) and keeps the module, aggregate, and record names in PascalCase, plural for aggregate folders; `Domain/{Aggregates}/Events/` is the stated exception, grouping the domain event types of one aggregate inside the module. A module whose single aggregate has the module's name stays flat. A single modules project holding every module stays allowed with `LS2020` as its boundary. LiteSpec supports one architecture style: the only project choice is one project per module or one modules project.

Every port of the module lives in its own `Ports/{Port}/` folder holding the interface `I{Port}` and only the types its signatures name, with no files directly in `Ports/`, whether one use case or many call it, so `Ports/` is the complete list of what the module needs from outside. Each port has exactly one adapter folder in `Infrastructure/` with the same name: `Infrastructure/` holds `Persistence/` and one folder per port it implements, nothing else. A port to an external system spells the external-system record name in PascalCase, and an in-process port takes a name for its capability, still pairing one port folder with one adapter folder. A port is an interface the module declares for something it does not compute in memory: an external system, a file format it reads or writes, a platform service the Platform does not already expose as an abstraction, or the clock. A `Ports/` folder that accepts in-process helpers becomes the place for whatever fits nowhere else, so each port earns its folder by reaching outside the process.

## Consequences

The Kernel holds the business values every module speaks with no dependency on any library. The Platform holds the technical capabilities with no business words and references no module. Each module is one project with its entry type, Contracts, Domain, Application, Ports, Infrastructure, and WebApi.

`Application/` and `WebApi/` each hold one plural aggregate folder with one folder per use case inside it, plus one folder per module-level use case. Only Contracts and the entry type are public, and hosts compose modules through AddModules.

The record tree stays, with use case records mapping to their aggregate and layer folders and aggregate records to their plural Domain folder. Code drops every typed container folder of the record tree and keeps module, aggregate, and record names, so each record path maps to code by one rule. A single modules project stays allowed with LS2020 as its boundary.

Every port of the module lives in its own `Ports/{Port}/` folder holding the interface `I{Port}` and only the types its signatures name, with no files directly in `Ports/`, and each port has exactly one adapter folder in `Infrastructure/` with the same name; `Infrastructure/` holds `Persistence/` and one folder per port it implements. A port to an external system spells the external-system record name in PascalCase, and an in-process port takes a name for its capability. A port is an interface the module declares for something it does not compute in memory: an external system, a file format it reads or writes, a platform service the Platform does not already expose as an abstraction, or the clock; in-process logic, store reads, wrappers over Platform abstractions, duplicate interfaces over one service, permission constants, and domain exceptions and enums are not ports, because a `Ports/` folder that accepts them becomes the place for whatever fits nowhere else. `Infrastructure/Persistence/` holds only module-wide store setup, and each aggregate's repository implementation, stored documents, and mapping sit in `Infrastructure/Persistence/{Aggregates}/`. The module options class lives in `Application/Settings/`. `Domain/` is absent when the module declares no aggregate, `WebApi/` when no use case is reached over HTTP, and `Ports/` when the module declares no port. `code-placement-drift` reports a file directly in `Ports/`, a port folder holding no interface or more than one, a misnamed port folder, a port folder that does not spell its external-system record name, a port or adapter folder naming a declared module, a type no interface signature names, a port with no adapter folder, an adapter folder with no port, a repository implementation outside its aggregate's `Persistence/` folder, and a use-case model or adapter in `Persistence/`.

The names come from three established patterns. The Kernel takes its name from the Shared Kernel pattern in Eric Evans's *Domain-Driven Design* (2003), a small shared part of the model that changes only by agreement, without the word Shared, because everything in it is shared and one product is one bounded context. The Platform follows the Microservice Chassis pattern Chris Richardson describes on microservices.io, the technical base that handles cross-cutting concerns so each service holds only business code; it is named Platform because modules contribute to it and hosts call `AddPlatform`. Port comes from Alistair Cockburn's "Hexagonal Architecture" (2005), also called Ports and Adapters: the application talks to the outside only through purpose-named ports, and adapters convert between a port and a technology. The same idea appears as Fowler's Gateway and Separated Interface, Palermo's Onion Architecture, and Martin's Clean Architecture, all resting on dependency inversion: the inner code owns the interface, the outer code implements it. "Port" is used instead of "Gateway", which fits an external system but less a file format or the clock, and instead of "Interfaces" or "Abstractions", which say nothing about why these interfaces are grouped. The [.NET Architecture](../../../backend/dotnet/architecture.md) page lists the other names considered.

## Revisit Conditions

This decision reopens when a module outgrows the layout, when project-per-module costs outweigh compiler-enforced boundaries, or when the layer folders stop matching the shape .NET readers expect.

Any of those cases means the layout no longer fits the products built on it. The team then decides again how backend code is organized.
