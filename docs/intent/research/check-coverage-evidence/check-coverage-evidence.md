# Check Coverage Evidence

LiteSpec's checker reads a built model and reports findings. Each finding names a check that a record failed. This research record counts which links and parents the checker enforces, which it only reports, and which no check reads at all. It takes the counts from the largest consumer project, which uses LiteSpec. A clean model report can mean that a rule is satisfied, waived, or never run. The report alone does not show which.

## Findings

The checker runs many checks below a requirement and almost none above it (`model`, `checker`). No check reads a feature's goal, a requirement's origin, a rule's `fulfills` link, or a flow's goal (`model`, `checker`). Those 4 unchecked links contain the largest measured gaps in the largest consumer (`model`, `checker`).

On 30 October 2026, the consumer's built model contained 2,711 open findings and 328 known findings (`checker`, `finding`). This record counts a check when its predicate tests a written link, its containment, its reverse orphan direction, or a computed trace (`model`, `checker`). For a written link, the predicate tests existence, resolution, target type, or reachability (`model`, `checker`). For containment, it tests identifier or folder (`model`, `checker`).

Checks fully cover resolution below a requirement (`model`, `checker`). Dangling record citations, body Markdown links, link target types, identifier homes, and step and operation fragments each have a tier G code (`checker`, `finding`). All of them show no findings (`checker`, `finding`). Requirement and flow checks cover fulfillment (105 known, none open), measurement, reach, state reachability, and transitions (`model`, `checker`).

Containment checks cover success results, scenario results, calculation tables, and reaction triggers, and all show no findings (`model`, `checker`). Orphan checks cover the 5 Behavior types that have neither parent, unserved steps, screened steps (91 known), screen serve mismatches, and effect loops (`model`, `checker`). Data and governance checks cover consistency rules, widening justification (6 open), erasure, retention, setting defaults, reservation releases, notification senders, exception fallbacks, and quality alerts (`model`, `checker`).

The code, screen, store, and operations traces also run many checks (`model`, `checker`). They cover marks and their resolution, followed decisions (8 open and unfollowed, 15 advisory without a basis), and unimplemented aggregates (21 open) (`model`, `checker`). They cover reactions, jobs, and external systems, unexposed use cases (60 open), and unimplemented use cases (8 open) (`model`, `checker`). They also cover declared effects that no dispatch takes (412 advisory), uncalled aggregate methods (165 open), and unreached use cases (182 advisory) (`model`, `checker`). The checker reports advisory findings without blocking (`checker`, `finding`).

The same traces cover unshown refusals (911 advisory), unconfirmed proofs (90 open, with 50 known), duplicated proofs (237 advisory), unthrown refusals, and contract mismatches (`model`, `checker`). They also cover alerts, settings, templates, and dependencies (`model`, `checker`).

A clean result can have 4 causes, and only the first means the rule holds (`checker`, `finding`). Satisfied checks have complete data (`model`, `checker`). No in-scope record lacks both parents, no step is unserved, and every reaction trigger resolves (`model`, `checker`). The sender, fallback, reservation, and serve checks agree with independent counts (`model`, `checker`).

Covered checks emit findings, and named waivers suppress those findings (`checker`, `finding`, `suppression`). A waiver suppresses findings only while it stays unexpired (`suppression`). The covered checks are the unfulfilled requirements, the unscreened steps, the unmeasured requirements, and the undeclared and unconfirmed families (`checker`, `suppression`).

Gated or scoped checks never run their predicate (`model`, `checker`). Flow reach exempts background-only use cases (`model`, `checker`). Of the checks, 2 run only at large size (`model`, `checker`). The transition check skips stores that have no transitions (`model`, `checker`). The checker exempts decision codes by folder in opposite directions (`model`, `checker`). `record-link-missing` covers only 5 Behavior types, and screen checks skip screens without a route (`model`, `checker`). Dependency and template checks return without a finding when they are not configured, so their clean tallies hide whether each check passed or never ran (`model`, `checker`).

The checker lacks some checks (`model`, `checker`). Only the analyzer emits `partial-missing`, so a waiver that names it would itself draw `gap-finding-unknown` (`checker`, `finding`, `suppression`). One working check passes more than its standard allows (`model`, `checker`). `state-unreached` passes a state that is a transition source or target (`model`, `checker`). The standard means a state that no transition reaches, so the check hides 9 states that have no incoming transition (`model`, `checker`).

Almost no check runs above a requirement (`model`, `checker`). No check reads a feature's goal link, and 28 of 40 features name no goal (`model`, `checker`). No check reads a requirement's origin, and 719 of 925 live requirements name neither `feature` nor `basedOn` (`model`, `checker`). No check reads a rule's `fulfills` link (`model`, `checker`). Of 2,295 rules, 2,052 have no direct links, and 79 still have none even when transitive fulfillment through governed use cases and aggregates counts (`model`, `checker`). No check reads a flow's goal, and all 112 goals are prose sentences (`model`, `checker`).

Other unchecked links each have a measured size (`model`, `checker`). No check reads flow `fulfills`, although all 112 flows carry it (`model`, `checker`). The reverse orphan of `solves` covers 1 unsolved problem (`model`, `checker`). Of 3 product decisions, 2 lack `basedOn` (`model`, `checker`). Bare-code rule refusals match no result code in 206 of 1,631 cases (`model`, `checker`). No use case raises one domain event, and one permission is allowed but never granted (`model`, `checker`).

The record also measures more unchecked links (`model`, `checker`). The reverse of `scenario.result` covers 2,330 written results, of which 62 are success results and 2,268 are refusals (`model`, `checker`). Of 49 outbound operations, nothing calls 9 (`model`, `checker`). Of the outbound integration events, 8 translate nothing, and nothing consumes 2 inbound integration events (`model`, `checker`). Of the notification claims, 33 stand on 28 notifications without a requirement (`model`, `checker`). Of 73 jobs, 15 have no runbook (`model`, `checker`). The reverse orphan of `basedOn` covers 4 constraints and 15 of 29 research records (`model`, `checker`).

Containment by identifier is otherwise complete (`model`, `checker`). The one empty parent, `module/hosting`, follows a recorded exception, not unrecorded drift (`model`, `checker`). 3 populations look orphaned but need no check (`model`, `checker`). They are orchestration use cases with no aggregate, store aggregates that only code reads, and uncited glossary terms, whose home is the glossary itself (`model`, `checker`).

The investigation proposes new finding codes in the existing naming pattern (`model`, `checker`, `finding`). Each code starts advisory (`checker`, `finding`). The codes are `feature-goal-missing` (28), `requirement-without-basis` (719), `rule-fulfills-nothing` (2,052 direct and 79 transitive), `flow-goal-unlinked` (112, after the field change), and `problem-unsolved` (1) (`checker`, `finding`). They also include `result-scenario-missing` (2,330, with the 62 success results as the first slice), `rule-refusal-unresolved` (206), and `domain-event-unraised` (1) (`checker`, `finding`).

The remaining proposed codes are `permission-unused` (1), `operation-uncalled` (9), `integration-event-untranslated` (8), `integration-event-unconsumed` (2), `claim-unlinked` (33 entries), and `job-without-runbook` (15) (`checker`, `finding`). The record also proposes that `record-link-missing` extend to flows, which covers none (`model`, `checker`). It proposes that `decision-basis-missing` extend to product decisions (2 more), and that `state-unreached` become incoming-only, starting advisory (9) (`model`, `checker`).

The recommendation has 2 refinements (`model`, `checker`). The cheap measurable form of requirement origin is the union of `feature` and `basedOn`, because `feature` alone is deliberately narrow (`model`, `checker`). The flow goal link needs a LiteSpec field change before a check, because no field exists for a checker to read (`model`, `checker`).
