# Native Command Line Evidence

## Answer

Measured on 2026-11-09 against release 4.0.0, publishing [the CLI project][cli-project] with `PublishAot` succeeded with 155 warnings: 77 IL2026, 77 IL3050 and one IL3000. All but the IL3000 sat in the CLI's own JSON code, at 77 call sites. Roslyn, YamlDotNet, JsonSchema.Net and Markdig reported none. The one IL3000 came from Roslyn's command-line compiler driver, `CommonCompiler.GetAssemblyLocation`, which the CLI never calls. The native executable ran `--help`, `--version`, `rules`, `init` and every text `model check` with output byte-identical to the build on the .NET runtime.

The JSON call sites were the one real defect. With reflection-based serialization off, as Native AOT sets it, `model check`, `model query` and `book` stopped with an error. With reflection forced back on, they exited 0 and wrote each finding as `{}`: the trimmer had removed the anonymous types' property metadata, so `model check --format json` on the small fixture wrote 239 bytes instead of 9,520. Building every JSON document as a node tree removed all 154 warnings and kept each output byte for byte. After that rewrite, the native executable passed all 1,756 CLI tests on win-x64 in 3 min 8 s, against 5 min 15 s for the suite on the .NET runtime. A full `model check` of the Claimwick example took 1.32 s native against 2.80 s on the runtime, as the mean of eight runs on one Windows machine.

[The cross-compilation page][native-aot-cross-compile] states that Native AOT builds for no other operating system, and for another architecture only with that architecture's linker. A linux-x64 executable built on Ubuntu 24.04, with glibc 2.39, failed to start on Debian 12 and Ubuntu 22.04 with `GLIBC_2.38 not found`. The same build on AlmaLinux 8, with glibc 2.28, ran on AlmaLinux 8, Ubuntu 22.04 and 24.04, and Debian 12 and 13, and its `rules` output matched the Windows output byte for byte. On a bare Debian 12 image, `model check` aborted with `No usable version of libssl was found`, because the CLI computes SHA-256 hashes, which .NET implements through OpenSSL on Linux; it passed once `libssl3` was installed. With invariant globalization, the executable linked only `libc` and `libm`. The glibc executable did not start on Alpine, which needs a musl build of its own.

[The RID-specific tools page][rid-specific-tools] states that the .NET 10 SDK packs one package per runtime identifier behind a top-level package, that a Native AOT package is packed on its own operating system, and that the platform packages publish before the top-level one. A local test confirmed that the platform package carries the release beside the executable, and that `dotnet litespec` installed from it runs the native executable. The runtime identifier graph maps `linux-musl-arm64` onto `linux-arm64`, so without a `linux-musl-arm64` package an Alpine arm64 machine would install the glibc executable, which cannot start there.

[The ILCompiler advisory][ilcompiler-advisory] lists `Microsoft.DotNet.ILCompiler` below 10.0.14 as vulnerable. `PublishAot` adds that package at the runtime version the SDK bundles, so the NuGet audit fails every restore on an SDK that bundles an earlier runtime, such as 10.0.113. SDK 10.0.114 is the lowest that bundles 10.0.14.

## Notes on Sources

Four sources were read on 2026-11-09. `rid-specific-tools` is the .NET documentation on RID-specific, self-contained and AOT tools, read for the package layout, the per-platform packing rule and the publish order. `native-aot-cross-compile` is the .NET documentation on Native AOT cross-compilation, read for the operating system and architecture limits and the linker each platform needs. `ilcompiler-advisory` is the GitHub advisory for the ILCompiler package, read for the vulnerable range and the first patched version. `cli-project` is the CLI project file, read for the trial build. The warning counts, the distribution runs and the timings are the researcher's own measurements, carried in the Answer.
