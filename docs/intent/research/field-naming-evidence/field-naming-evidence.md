# Field Naming Evidence

Every LiteSpec record is a set of named fields. A field name tells a reader what kind of value the field contains. This research record counts where one field name carries 2 meanings and where one meaning carries 2 names. It covers the schemas, the templates, and the largest consumer, a project that uses LiteSpec. Readers and checks both rely on each name meaning one thing. The record finds 5 collisions that produce misleading or invalid consumer data.

## Findings

The field set is mostly systematic, and 5 collisions cause real damage [record schema][record-schema] [glossary schema][glossary-schema]. The consumer shows invalid or misleading data from 2 collisions [record schema][record-schema]. The field set uses one shared header and one suffix grammar, and its link names each carry one meaning [record schema][record-schema] [glossary schema][glossary-schema].

All 37 page types share one header: `type`, `id`, `title`, `terms`, and the type's own fields [record schema][record-schema] [glossary schema][glossary-schema]. Links are present-tense verbs, and they are plural when they contain arrays [record schema][record-schema] [glossary schema][glossary-schema]. `fulfills`, `governs`, `solves`, `decides`, and `basedOn` each carry one meaning everywhere [record schema][record-schema]. Every field name in both schemas is camelCase or a single lowercase word [record schema][record-schema] [glossary schema][glossary-schema]. A program parses the field inventory from the schemas [record schema][record-schema] [glossary schema][glossary-schema].

Multiword names follow a suffix grammar [record schema][record-schema] [glossary schema][glossary-schema]. `<verb>By` names a deadline, `<verb>On` names an event date, `<verb>When` names a condition, and `<verb>Because` names a justification [record schema][record-schema] [glossary schema][glossary-schema].

The first collision is 2 status-like fields with unrelated values [record schema][record-schema]. The record header field takes one value on all 111 consumer features [record schema][record-schema]. The feature offer field takes 4 values [record schema][record-schema]. The field `states` also names aggregate state entries [record schema][record-schema].

The second collision is that bare `by` names 2 kinds of value [record schema][record-schema]. Goals require a date, and requirements take dates [record schema][record-schema]. Features take milestones, such as `v1` and `M1 Evidence`, which appear in all 39 live records, under a plain string type [record schema][record-schema]. Beside it, 4 sibling fields follow the `<verb>By` pattern [record schema][record-schema]. All 111 features carry milestone-style `by` values where the surrounding convention expects dates [record schema][record-schema].

The third collision is that `source` carries 5 meanings [record schema][record-schema]. It marks the origin on 13 page types and on most entries, about 2,900 consumer fields [record schema][record-schema]. It contains a constraint's free-text outside source [record schema][record-schema]. It names the CloudEvents source of an integration event [record schema][record-schema]. It contains a nested input origin enum and a nested output origin aggregate array under a singular name [record schema][record-schema]. `research.sources` is a sixth shape beside them [record schema][record-schema].

The fourth collision is that `serves` covers 3 target sets across 1,807 records [record schema][record-schema]. A feature serves goals, a use case, reaction, or job serves steps or goals, and a screen serves steps [record schema][record-schema]. A feature contributes to a goal, while a use case names the step it serves [record schema][record-schema].

The fifth collision is that `goal` is both a record type and a required prose sentence on all 112 flows [record schema][record-schema]. The flow link change resolves it [record schema][record-schema].

The consumer shows invalid or misleading data from 2 collisions [record schema][record-schema]. All 111 features carry milestone-style `by` values where the surrounding convention expects dates [record schema][record-schema]. Of the use-case `serves` values, 11 name a whole flow, where the schema allows only a flow step or a goal [record schema][record-schema].

The record judges several smaller overloads as keep-and-document [record schema][record-schema]. `steps` on flows and `steps` on coordination aggregates overlap, so LiteSpec renames the aggregate side, which touches 6 records [record schema][record-schema]. `values` on requirements and terms overlap, so the term side becomes `codes` [record schema][record-schema] [glossary schema][glossary-schema]. Exceptions and integration events share `subject` [record schema][record-schema]. `scope`, `check`, and `code` keep consistent cores [record schema][record-schema].

The `*Because` suffix needs repair only where it contains links [record schema][record-schema]. The nested `consistency.because` contains a rule list, and `wideningBecause` contains a requirement link [record schema][record-schema]. Both become verb-form link names [record schema][record-schema]. The effect-level `onFailure` is a string, while the page-level `onFailure` is a structured object [record schema][record-schema]. This is the most mechanical inconsistency in the schemas [record schema][record-schema] [glossary schema][glossary-schema]. The effect-level string takes the structured shape or the name `onFailurePolicy` [record schema][record-schema].

The investigation also finds schema drift outside the brief [glossary schema][glossary-schema] [glossary template][glossary]. The consumer glossary template requires `layer` and `aliases` on every term [glossary template][glossary]. The glossary schema defines neither, and it forbids extra properties [glossary schema][glossary-schema]. The template `schemaVersion` 3 contradicts the schema `const` 2 [glossary template][glossary] [glossary schema][glossary-schema]. All 508 consumer terms carry `layer`, so the schema is out of step [glossary schema][glossary-schema] [glossary template][glossary].

The consumer carries fields that LiteSpec never defines [record schema][record-schema]. They are `result.kind` with 163 uses, which duplicates `outcome`, `setting.readBy` with 15, and `notification.sentBy` with 8 [record schema][record-schema]. They also are `notification.personal` with 9, `job.errorBackoff` with 4, `job.startupDelay` with 3, and `rule.writes` with 33, always empty [record schema][record-schema]. The record calls these consumer inventions [record schema][record-schema]. The link-shaped names show authors seeking vocabulary that LiteSpec does not offer [record schema][record-schema].

The proposed naming rule is one concept, one name, one shape, everywhere it appears [record schema][record-schema] [glossary schema][glossary-schema]. A field name keeps one concept, one value kind, and one cardinality on every record that carries it [record schema][record-schema] [glossary schema][glossary-schema]. New fields follow the existing grammar [record schema][record-schema] [glossary schema][glossary-schema]. A classifier is `kind` [record schema][record-schema] [glossary schema][glossary-schema]. A link is a present-tense verb, plural when it contains an array [record schema][record-schema] [glossary schema][glossary-schema]. A deadline is `<verb>By`, and a recorded date is `<verb>On` [record schema][record-schema] [glossary schema][glossary-schema]. A justification is `reason` or `rationale`, never a `*Because` field that contains links [record schema][record-schema] [glossary schema][glossary-schema].

The rule also fixes the other word classes [record schema][record-schema] [glossary schema][glossary-schema]. The defining sentence of a named thing is `meaning`, and the normative sentence of a promise is `statement` [record schema][record-schema] [glossary schema][glossary-schema]. A group nests as an object only when its fields always appear together [record schema][record-schema] [glossary schema][glossary-schema]. A name that a record type carries is never reused for a prose field [record schema][record-schema] [glossary schema][glossary-schema]. The maintainer validator checks the mechanical half of the rule, which covers same type, plural as array, and `*By` and `*On` as dates [record schema][record-schema] [glossary schema][glossary-schema]. The judgment half stays a reviewed provision [record schema][record-schema] [glossary schema][glossary-schema].
