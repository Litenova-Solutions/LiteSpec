# Cross-Module Coupling Practice

LiteSpec 6.0.0 organizes a modular monolith by module, aggregate, and use case. It lets a use case run another use case inline, publish its own integration events, and read another module through a read port. This research record compares that shape with outside practice and with what one large consumer built under it. The record read both on 14 November 2026. Each allowance looked small on its own, but together they grew shared folders and coupled modules that the rules meant to keep apart.

## Findings

Outside practice keeps coupling inside a slice and out of the space between slices [vertical slice architecture][jimmybogard-vertical-slice-architecture]. Bogard's 2018 article states the aim as minimal coupling between slices and maximal coupling inside one [vertical slice architecture][jimmybogard-vertical-slice-architecture]. So a slice that names another slice's request type couples to that slice's reasons to change [vertical slice architecture][jimmybogard-vertical-slice-architecture].

A module learns another module state without asking for it [event-driven article][martinfowler-articles-201701-event-driven]. Fowler's 2017 article names the pattern event-carried state transfer [event-driven article][martinfowler-articles-201701-event-driven]. A receiver keeps its own copy of the needed data, filled from owner events, and stops calling the owner [event-driven article][martinfowler-articles-201701-event-driven]. The receiver maintains that copy and accepts that it lags the owner [event-driven article][martinfowler-articles-201701-event-driven].

A port is a seam the core declares for something outside it [hexagonal architecture][cockburn-hexagonal-architecture]. Cockburn's 2005 article on ports and adapters, also called hexagonal architecture, places a port where the application meets a driver or a driven system [hexagonal architecture][cockburn-hexagonal-architecture]. The port lets adapters change behind it [hexagonal architecture][cockburn-hexagonal-architecture]. A repository and an outside system fit that shape [hexagonal architecture][cockburn-hexagonal-architecture]. By contrast, a reader that one module calls to fetch another module state is an in-process service call [hexagonal architecture][cockburn-hexagonal-architecture]. It runs between two parts of one core, not as a seam to the outside [hexagonal architecture][cockburn-hexagonal-architecture].

A published modular monolith reference separates the two kinds of message [modular monolith reference][github-kgrzybek-modular-monolith-with-ddd]. The repository keeps domain events inside the module that raised them [modular monolith reference][github-kgrzybek-modular-monolith-with-ddd]. It crosses module boundaries with integration events processed in their own transactions [modular monolith reference][github-kgrzybek-modular-monolith-with-ddd]. It runs follow-on work inside a module as internal commands from its own processing [modular monolith reference][github-kgrzybek-modular-monolith-with-ddd]. No module sends another module's command [modular monolith reference][github-kgrzybek-modular-monolith-with-ddd].

One large consumer with 43 modules and 1,541 use-case folders shows what the allowances built [application page][application] [dotnet architecture page][dotnet-architecture]. About 270 files in aggregate `Application/` folders hold use-case messages and results outside their folders [application page][application] [dotnet architecture page][dotnet-architecture]. A second use case names those messages, placing them outside their own folders [application page][application] [dotnet architecture page][dotnet-architecture]. 214 files stand in module `Contracts/Commands/` folders [application page][application] [dotnet architecture page][dotnet-architecture]. Other modules name 104 commands outside their module [application page][application] [dotnet architecture page][dotnet-architecture]. 101 refusal types stand in `Contracts/Exceptions/`, and other modules throw 72 of them [application page][application] [dotnet architecture page][dotnet-architecture].

The same consumer shows 57 inline edges in 47 use-case records [application page][application] [dotnet architecture page][dotnet-architecture]. 33 command handlers hold a mediator [application page][application] [dotnet architecture page][dotnet-architecture]. Running a command inside another command transaction needs a nested dispatch scope with two ambient values and a per-message aggregate cache [application page][application] [dotnet architecture page][dotnet-architecture]. It also needs reload methods that avoid stale reads [application page][application] [dotnet architecture page][dotnet-architecture]. 69 handlers publish their own integration events, built from the aggregate rather than from the fact the act raised [application page][application] [dotnet architecture page][dotnet-architecture].

Cross-module readers show the largest coupling [application page][application] [dotnet architecture page][dotnet-architecture]. 741 files of other modules name 86 reader interfaces in `Contracts/Ports/` folders [application page][application] [dotnet architecture page][dotnet-architecture]. They are 274 command handlers, 148 query handlers, 114 reactions, and the rest in services and steps [application page][application] [dotnet architecture page][dotnet-architecture]. The busiest reader has 18 methods, several named for their one caller [application page][application] [dotnet architecture page][dotnet-architecture]. This suggests that a screen that calls each owner's query answers a query handler that only shows another module's data with less coupling [application page][application] [dotnet architecture page][dotnet-architecture].

Trigger folders split what one use case does [application page][application] [dotnet architecture page][dotnet-architecture]. 232 folders named for a fact contain event handlers [application page][application] [dotnet architecture page][dotnet-architecture]. 22 facts have such folders in more than one module, so a fact folder never shows every reaction to its fact [application page][application] [dotnet architecture page][dotnet-architecture]. Each handler names the command of a use case in another folder, which moves those commands to shared folders [application page][application] [dotnet architecture page][dotnet-architecture].
