# Intent Hierarchy Evidence

The Intent layer holds the reasons a product exists, such as the product, its goals, problems, features, requirements, constraints, research, decisions, and flows. This research record checks which links connect Intent records, which of them LiteSpec requires and checks, and how other tools and the largest consumer group their requirements. The largest consumer is a project that uses LiteSpec. It matters because 719 of 928 requirements in that consumer name no origin, and the current rules do not count that as a defect.

## Findings

Above the requirements, LiteSpec hierarchy rests on rationale prose rather than on required or checked links [Intent page][intent] [record schema][record-schema] [model tool page][model-2]. In the largest consumer, 719 of 928 requirements name no origin [record schema][record-schema]. The record states that every enforced Intent check passes in that consumer [model tool page][model-2].

The schema requires only 4 Intent links, and a check enforces each of them [record schema][record-schema] [model tool page][model-2]. They are `product.audience`, `flow.actor`, a requirement `except` entry to its `fallback`, and `decision.decides` on product decisions [record schema][record-schema] [model tool page][model-2]. The provision and the check require `decision.decides` even though the schema leaves it optional [Intent page][intent] [model tool page][model-2] [record schema][record-schema]. Every other link above the requirements is optional in the schema, is mentioned only in the provision rationale, and is unchecked [Intent page][intent] [record schema][record-schema] [model tool page][model-2]. The record reads each cell from the schema, the provision text, and the check table [Intent page][intent] [record schema][record-schema] [model tool page][model-2].

One layer below Intent, LiteSpec already applies the principle that every record points up [Intent page][intent] [model tool page][model-2]. A use case with neither `serves` nor `fulfills` fails `record-link-missing` at tier G [model tool page][model-2]. LiteSpec applies the principle nowhere inside Intent [Intent page][intent] [model tool page][model-2].

The central measured gap is that 719 of 928 requirements name neither `feature` nor `basedOn` [record schema][record-schema]. Of 928 requirements, 56 name a `feature`, 164 name `basedOn`, and 11 carry both [record schema][record-schema]. The absence of `feature` alone is not a defect, because the field is defined narrowly [record schema][record-schema] [Intent page][intent]. It names the feature that carries the requirement in a named phase, so a built requirement correctly carries none [record schema][record-schema] [Intent page][intent].

The combined absence is still not a conformance defect today either [Intent page][intent] [model tool page][model-2]. The provision puts the expectation in its rationale [Intent page][intent]. Its statement and its check require only the identifier, `kind`, `statement`, and dated applied values [Intent page][intent] [model tool page][model-2] [record schema][record-schema]. So the record counts the 719 as specification-tolerated traceability defects [Intent page][intent] [model tool page][model-2] [record schema][record-schema]. They are the fault of LiteSpec's missing obligation and missing check, not of the consumer's authors [Intent page][intent] [model tool page][model-2].

One measured signal shows that the anchor already matters in practice [record schema][record-schema] [model tool page][model-2]. Of 150 requirements that nothing below fulfills, all 100 without a `feature` appear as known `requirement-fulfillment-missing` findings [record schema][record-schema] [model tool page][model-2]. None of the 50 with a `feature` produces such a finding [record schema][record-schema] [model tool page][model-2].

Requirements follow 3 different groupings, so one feature story spreads over 3 files [Intent page][intent] [model page][model] [record schema][record-schema]. A requirement page groups commitments by area [model page][model] [record schema][record-schema]. A feature groups an offer under a problem [Intent page][intent] [record schema][record-schema]. A flow groups steps under a goal [Intent page][intent] [record schema][record-schema]. The flow that walks it sits under a third record [Intent page][intent] [record schema][record-schema].

The record proposes that each feature hold its requirements as entries [Spec Kit templates][mintlify-github-spec-kit-advanced] [OpenSpec concepts][openspec-docs-core-concepts] [Kiro concepts][kiro-docs-specs-concepts] [record schema][record-schema]. A requirement has 3 origin fields with a precedence rule, where one ordered list suffices [record schema][record-schema]. The origin is the first `features` entry, otherwise the first `basedOn` entry, otherwise a decision that names the requirement in `decides` [record schema][record-schema]. A goal is never a requirement reason at all [record schema][record-schema].

Goal-oriented practice refines goals directly into requirements [solution tree glossary][producttalk-glossary-discovery-opportunity] [impact mapping page][techtarget-searchsoftwarequality-definition]. Impact mapping traces deliverables to a goal through an actor and an impact [impact mapping page][techtarget-searchsoftwarequality-definition]. With the feature as the parent, the precedence rule serves no purpose [record schema][record-schema]. So the record proposes that a requirement name its reasons in one `cites` list [record schema][record-schema] [solution tree glossary][producttalk-glossary-discovery-opportunity] [impact mapping page][techtarget-searchsoftwarequality-definition]. The list holds any of goal, problem, feature, constraint, research, and decision, in no order of precedence [record schema][record-schema]. A requirement that cites nothing fails `requirement-cites-missing` at tier G [model tool page][model-2].

Fulfillment and constraint answers each get one home [Intent page][intent] [model page][model]. A flow alone clears `requirement-fulfillment-missing`, because the checker counts rule, use case, and flow as fulfilling [model tool page][model-2]. The record proposes that only Behavior records fulfill a requirement [Intent page][intent] [model tool page][model-2]. Those are the rule, use case, reaction, job, notification, and setting [Intent page][intent]. A flow names the requirements it shows in `carries` [record schema][record-schema].

Authors write a constraint answer twice, once as prose under What It Requires and once as requirement entries that cite the constraint [Intent page][intent] [record schema][record-schema]. Of 29 constraints, 5 are cited by none [record schema][record-schema]. So the record proposes that What It Requires become a generated region that lists the requirements citing the constraint [Intent page][intent] [record schema][record-schema]. A constraint with `applies` set to true that no requirement cites is `constraint-unreached` at tier G [model tool page][model-2]. Volere supports this shape by treating a mandated constraint as a requirement with its own rationale and fit criterion [Volere template][inf-ed-ac-teaching-courses-seoc].

Names take their outside meaning [INCOSE slides][incose-wp-content-uploads-legacy] [ReqView templates][reqview-homepage-netlify-doc-iso-iec-ieee-29148]. LiteSpec `kind` for business requirements holds dated values, such as a receipt threshold or a price [record schema][record-schema].
