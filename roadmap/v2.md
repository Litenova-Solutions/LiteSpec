# Standards v2

A design document for the next generation of the Litenova Engineering Standards. This is not an execution plan. It is the discussion, the alternatives that were considered, the rationale for the recommended direction, and the questions still open. A plan follows from this document when the direction is settled.

## Background

### What v1 set out to be

The Litenova Engineering Standards started as an attempt to write down the rules a single engineering team would follow. It grew into a contract that a team of agents operating on a consumer project would read before changing code. Two design choices defined v1.

The first choice was Markdown everywhere. Humans and LLMs both read it. Git diffs it cleanly. Every documentation tool renders it. The second choice was a Git submodule for delivery. Pinning a tagged release in a submodule is the simplest mechanism that gives a consumer a reproducible contract at a specific version.

Everything else followed. A page contract that fits Markdown. A validator that parses Markdown. A per-page Agent Summary section as the projection an LLM reads first. A consumer manifest at `standards.project.json`. Four validator scripts in the standards repository.

### What v1 produced

The v1 repository carries 107 hand-written Markdown files across 11 areas. It has 28 consumer templates and 5 standards-authoring templates. It has 10 JSON Schemas. The validator pipeline has five Node scripts. The contract has 899 named provisions with stable identifiers. Every consumer specification opens with a JSON metadata block validated against a schema. Every rule has a verification row.

A reader of the standards can resolve any cited provision in one step through the generated `provisions.md` index. A consumer can mechanically check conformance against any release. An agent can read the Agent Summary of a page and know the page's most important rules.

### What triggered the v2 thinking

Three observations accumulated over the life of v1.

The duplication grew. Every page carries the same provision three times: as an Agent Summary bullet, as a Standards section H3, and as a Verification table row. The three copies drift. The validator has to keep them in sync. The work of authoring has tripled for every rule.

The Agent Summary projection became the wrong abstraction. It was added so an agent could read one section and know what mattered. As provisions grew, the projection became a hand-maintained summary of a hand-maintained list of hand-written rules. An agent would be better served by asking the system directly.

The submodule became the wrong delivery mechanism. A consumer that runs an agent on its codebase does not naturally check whether its standards submodule is up to date. The README recommends pinning a tag; most consumers do not. The mechanism that worked for human version pinning does not work for agent version pinning.

The diagnosis is not "v1 is wrong." The diagnosis is "v1 solved the 2022 problem; the 2026 problem is different."

### Duplication math

Each provision appears three times in its page. It appears in the Agent Summary as a bullet ending with the rule ID. It appears in the Standards or Conventions section as an H3 with the same ID suffix. It appears in the Verification table as the ID column.

The Agent Summary citation list is a subset of the Standards list (typically the higher-tier rules). The Verification table covers every Standard and Convention on the page.

Across the 100 surveyed files: about 700 redundant Agent Summary citation entries. About 1500 redundant Verification table ID-column entries. 64 hand-written Intent sections that mostly restate the page's first heading.

The duplication is the cost of the page contract. The page contract is the value. The question is whether the contract can be satisfied with a smaller surface in the source.

### What peers do

For comparison, the documentation systems consulted during this design.

Kubernetes documentation (`kubernetes/website`) uses Concept, Task, Tutorial, and Reference page types with fixed section shapes. Frontmatter with weight drives ordering. The API reference is generated from OpenAPI. It is the model for typed page content.

AsciiDoc and Antora (`asciidoctor.org`, `antora.org`) provide native includes, attribute references, cross-references, and conditional content. They are the closest peer to structured prose. AsciiDoc is a v3 candidate.

DITA XML (`docs.oasis-open.org/dita/`) uses conref, keyref, and conditional content per audience. It is the canonical engineering documentation reuse model. It is cited as the design ideal even though the format is not adopted.

OpenAPI (`spec.openapis.org`) uses `$ref` for component reuse. Schema-first authoring drives generated docs and clients. It is the model for structured contract with generated views.

Vercel docs handbook (`vercel.com/design/guidelines`) recommends plan-then-write, content-type in frontmatter, TL;DR up top, active voice, contractions, and a banned word list. It is the model for tone.

Mintlify style guide (`mintlify.com/docs/guides/style-and-tone`) recommends second person, active voice, a 25-word sentence cap with judgment, terminology consistency, and automated linters. It is the model for controlled prose.

Stripe docs (`docs.stripe.com`) uses a three-pane layout: navigation, content, and runnable code. It is the gold standard for API documentation.

Linear docs (`linear.app/docs`) uses a card-grid hub with verb-led descriptions, a sidebar ordered by user mental model, and a peer philosophical site. It is the model for information architecture.

The peers converged on three patterns: structured authoring with generation, layered content types, and a thin separation between human and machine surfaces. v1 has the first pattern implicitly through the JSON metadata block. v2 makes it explicit.

## Diagnosis

### What works in v1

Six v1 design choices are above the peer median. They survive v2 unchanged.

Spec-as-code is real, not aspirational. Every consumer specification opens with a JSON metadata block validated against a JSON Schema. Every rule has an identifier. Every provision maps to a verification row. v2 keeps the JSON metadata block for consumer specs.

The reference cast works. Every Scenario section in the consumer docs draws from `docs/domain/scenarios.md`. One buyer, one organizer, one venue, one Saturday night. Scenarios accumulate instead of restarting. v2 keeps the cast and the pattern.

One word per concept is mechanically enforced. The consumer's language record plus the glossary plus the scope-bounded rejection rules prevent term-drift. v2 keeps the language schema and the enforcement.

Open modeling questions and Gaps are honest. The consumer's Order aggregate page states that nothing abandons an unpaid order but lists the transition with the use case that would do it. Most teams hide this kind of gap. v2 keeps the convention.

Decision records are structured. Context, decision, standards impact, activation conditions, review controls, consequences, known gaps. Stronger than Nygard's original three-section template. v2 keeps the shape.

Identifier systems are bidirectional and resolve. `INV-`, `POL-`, `VAL-`, `AUTZ-`, `AC-`, `E2E-` on the consumer side; `standards/<kind>/<page>.<slug>` on the standards side. A reader resolves any citation in one step. v2 keeps the grammar.

The vocabulary, the schema catalog, the validator pipeline semantics, the consumer template contract, and the page contract's section shape all survive.

### What does not work in v1

Four problems justify the v2 work.

Duplication. The page contract requires every provision to be authored three times. The validator has to keep the three copies in sync. The author has to write each one. The reviewer has to check each one. The duplication cost grows linearly with the number of provisions.

Implicit structure. Standards pages have no frontmatter. The Agent Summary anchor is added by hand. The `lastReviewed` date lives nowhere; it is implicit in the changelog. Profile Composition lists pages that the manifest also lists; either source can drift. The contract is implicit because Markdown carries no semantic primitives.

The submodule is hostile UX. Detached HEAD, easy to forget, inconsistent IDE handling, agents do not understand it. The standards recommend pinning a tag; most consumers do not.

No live validation feedback for agents. An agent operating on a consumer project reads the Agent Summary projection, hopes it is current, and proceeds. There is no way to ask the system "what rules bind to this command?" and get a precise answer.

### Five jobs the system serves

Underneath the duplication and the implicit structure, the system serves five distinct jobs.

First, a contract registry: 899 named assertions with IDs that consumers must satisfy.

Second, a schema catalog: 10 JSON Schemas for structured artifacts consumers produce.

Third, prose rationale: the "why" behind each rule, written in controlled English.

Fourth, a validator pipeline: Node scripts that mechanically check conformance.

Fifth, an agent contract: `AGENTS.md` plus per-page Agent Summary sections that an AI agent reads first.

Markdown carries the contract registry as prose, then validates it mechanically against an inferred shape. That works, but the inference is the cost. A structured authoring surface lets the validator check more without inference. A queryable agent affordance replaces the projection.

## Alternatives considered

Six alternative architectures were considered. Each is presented honestly with what it would solve and what it would cost.

### Alternative A: Keep Markdown, add structure inline

The smallest change. Keep the current one-file-per-page model. Add inline structure to each provision.

YAML frontmatter per page declaring `kind`, `area`, `lastReviewed`, `order`. HTML comment directives inside Standards and Conventions sections tagging each provision with its `tier`, `method`, and `evidence`. A build step that walks the directive comments and generates the Agent Summary and Verification table.

This solves the duplication. The author writes Standards and Conventions sections. The Agent Summary and Verification table are generated.

The cost is small but real. HTML comments are fragile in some editors. Markdown spec does not formally include them as content. The author has to remember the directive syntax. Per-page frontmatter makes the Agent Summary aggregation more complex than aggregating across per-provision files.

This path was not chosen. The recommended path gives the same payoff with cleaner authoring.

### Alternative B: Switch to AsciiDoc

Replace Markdown with AsciiDoc. AsciiDoc has built-in primitives Markdown lacks. `include::` for content reuse. Attribute references for substitution. Cross-references resolved at build time. Conditional content per platform. Semantic block types for requirement, rationale, and example.

This solves most of the duplication. AsciiDoc's includes and semantic blocks give native structure. Antora composes multiple repos into one site. The validator pipeline shrinks because AsciiDoc enforces more by spec.

The cost is the migration. AsciiDoc is less universal than Markdown. LLMs are less fluent in it. Every consumer updates tooling.

This path was not chosen for v2. If v3 considers a format migration, AsciiDoc is the target.

### Alternative C: Switch to structured JSON

Replace Markdown with JSON. Each provision is a structured record with id, kind, area, page, slug, requirement, rationale, evidence, example, method, tier, supersedes, supersededBy. The validator reads JSON directly. The Markdown is rendered.

This solves the validator drift. The validator cannot drift from the contract because both consume the same JSON. The Markdown cannot drift from the contract because the Markdown is generated. The duplication is gone by construction.

The cost is human authoring. JSON for prose-heavy fields is painful. Multi-paragraph rationale becomes escaped string noise. Examples become awkward. The user correctly called this path "diabolical" for human authoring.

This path was not chosen. JSON is right for the machine, wrong for the human.

### Alternative D: Generate from the compiler

Replace the hand-written standards with output from Roslyn analyzers and similar tools. Each analyzer emits a rule. The rule's prose is in the analyzer's source. The standards doc is generated.

This solves the rule-drift problem. Rules cannot drift from enforcement. The analyzer is the source.

The cost is scope. This only works for the standards that have a corresponding analyzer. Most cross-cutting standards have no analyzer: authoring, controlled prose, identifier grammar, page contract. They would still be hand-written in some form, and the two surfaces would drift.

This path was not chosen. Splitting the source makes both halves worse.

### Alternative E: Generate from the tests

Make every acceptance criterion a Reqnroll feature file. The standards document is generated from the feature files and their step definitions.

This solves the drift between standards and what is tested. Living documentation.

The cost is expression. Many standards have no executable test. Tests as documentation forces every rule into a feature file, which constrains expression. The "what" becomes "what can be tested" and loses the "why."

This path was not chosen. Tests are a partial view of the contract.

### Alternative F: Per-domain monorepos

Split the single standards repo into per-domain repos. A consumer depends on the domains it uses.

This solves surface size. Smaller surface per consumer. Clearer dependency graph.

The cost is coordination. Cross-cutting rules need a separate mechanism. Release coordination across multiple repos. The architecture becomes "core plus many satellites" which is more complex than "one contract."

This path was not chosen. The per-consumer benefit is small. The coordination cost is large.

### Why the recommended path

The recommended path is Markdown with YAML frontmatter, one file per provision, generated views. It is the smallest change that solves the duplication without sacrificing author ergonomics. It is the path that lets humans keep writing Markdown while the machine consumes structured JSON. It is the path that lets an agent ask the contract a precise question instead of reading a projection.

The other alternatives are not wrong; they are paths the recommended approach does not preclude. v3 could move from Markdown to AsciiDoc. A future v4 could split into per-domain repos. The recommended path leaves those doors open.

## The v2 architecture

### Core principle

Human writes Markdown. AI consumes structured data. The two surfaces are separated by a renderer.

The author writes one Markdown file per provision, with YAML frontmatter carrying structured fields. The body carries prose. The renderer reads the frontmatter, parses the body, and emits three views.

Markdown per page: the human-readable view, generated. HTML per page: the hosted view, generated. JSON per provision: the structured record for tools and AI, generated.

The author's only authoring surface is the Markdown file. The machine's only consumption surface is the JSON record. The Markdown and HTML are derived.

### Four-channel distribution

The v2 contract reaches its audiences through four parallel channels.

The contract directory in the standards repository: one Markdown file per provision. The single source of truth and the only thing contributors edit.

Packages: an npm package and a NuGet package carry the contract plus the validator and renderer. Consumers depend on the package instead of cloning a submodule.

Hosted docs: rendered HTML at a versioned URL. Searchable. The human-readable view, generated on every release.

Agent affordance: an MCP server and an HTTP API. Agents operating on consumer projects query these for exactly the rules that apply.

All four channels read the same contract. The contract is canonical. The channels are views.

### One file per provision

The unit of authorship changes from page to provision. A provision is one assertion with one identifier. It is small enough to fit on a screen. The diff for a one-line change is one line.

```
contract/
  backend/
    api/
      _page.yaml                                # page metadata + provision order
      use-one-endpoint-per-operation.md         # provision 1
      keep-endpoint-dependencies-transport-focused.md  # provision 2
      derive-authenticated-identity-from-claims.md    # provision 3
      ...
  core/
    authoring/
      _page.yaml
      apply-controlled-prose-measures.md
      ...
```

Why per provision rather than per page. A change to one rule is a diff of one file. The reviewer sees one rule. The PR conversation stays focused on one assertion. Each provision lives in exactly one place; the page is a virtual concept assembled at render time. The JSON output is per-record with no parsing across an implicit structure. A superseded provision is a file marked `supersededBy`; a new provision is a new file; the chain is in the frontmatter.

The cost is more files. For the current 899 provisions across roughly 100 pages, that is 100 `_page.yaml` files plus 899 provision files, organized by area. The structure is regular and discoverable; the file count is not the problem people assume it is.

### The provision file shape

A provision file is a Markdown file with YAML frontmatter. The body has four optional sections, in order: a requirement sentence, a rationale paragraph, a Deviation blockquote if the provision is SHOULD or SHOULD NOT, an Evidence blockquote, and an Example blockquote.

```markdown
---
id: standards/rule/backend-api.use-one-endpoint-per-operation
kind: rule
area: backend
page: api
slug: use-one-endpoint-per-operation
tier: high
method: static
supersedes: []
supersededBy: []
---

# Use one endpoint per operation

An API operation MUST live in exactly one HTTP endpoint.

Two routes for one operation make authentication and authorization decisions ambiguous.
Routing rules cannot tell which one to apply.

> `node tools/validate-standards.mjs` rejects a second route declaration.

> A POST to `/orders` and a POST to `/api/orders` both create orders.
> The second declaration is a violation.
```

Frontmatter fields.

`id` is the stable identifier in the format `standards/<kind>/<page>.<slug>`. Unchanged from v1.

`kind` is one of `invariant`, `validation`, `authorization`, `acceptance-criterion`, `policy`, or `rule`. Unchanged from v1.

`area` is the area directory. Unchanged from v1.

`page` is the page directory stem. Unchanged from v1.

`slug` is the kebab-case identifier slug. Unchanged from v1.

`tier` is `high`, `medium`, or `low`. Drives Agent Summary generation. New in v2.

`method` is `static`, `test`, `inspection`, or `operation`. Drives Verification table generation. New in v2.

`supersedes` and `supersededBy` are arrays of provision IDs. New in v2.

The body follows a simple grammar. The H1 carries the title. A requirement sentence carries one uppercase normative modal. A rationale paragraph explains why. Optional labelled blockquotes carry Deviation, Evidence, or Example. Anything else becomes the page's rendered prose.

### The page manifest

Each area/page directory carries one `_page.yaml`:

```yaml
area: backend
page: api
title: HTTP API
intent: One endpoint per operation, transport-focused dependencies, authenticated identity, and stable problem details.
order:
  - use-one-endpoint-per-operation
  - keep-endpoint-dependencies-transport-focused
  - derive-authenticated-identity-from-claims
  - reject-a-client-supplied-actor-identifier
  - authorize-the-target-resource
  - return-stable-problem-details
  - keep-error-responses-free-of-internal-detail
  - bound-collection-queries
  - state-an-unexpressible-transition-as-a-custom-method
  - apply-patch-to-a-partial-update
  - model-a-monetary-value-as-one-object
  - name-transport-fields-by-one-rule-set
  - treat-openapi-as-a-generated-contract
  - reflect-enforced-authentication-in-the-contract
  - mirror-a-domain-closed-set-as-a-transport-model-of-the-same-shape
  - reject-a-collapsed-or-borrowed-wire-contract
```

Fields.

`area` and `page` are directory location. Required.

`title` is the page's H1 in the rendered output. Required.

`intent` is the page's Intent section text in the rendered output. Required.

`order` is the slug order for provisions on this page. Required. A provision not listed here is not rendered on this page.

Optional fields to consider. `audience` lists who reads this page. `seeAlso` lists related page paths.

### The renderer

The renderer walks each `contract/<area>/<page>/`, reads the `_page.yaml`, then for each slug in `order` loads the corresponding `.md` file and emits the page Markdown.

Outputs. `rendered/<area>/<page>.md` is the page Markdown. `rendered/<area>/<page>.html` is the HTML. `dist/contract.json` is a single JSON file indexing every provision. `dist/manifest.json` is the generated manifest derived from `_page.yaml` files.

The renderer is a small library the CLI, the hosted docs service, and the MCP server all call. It is a function, not a build tool.

### What gets generated

For `contract/backend/api/` (16 provision files plus `_page.yaml`), the renderer produces:

```markdown

## Intent

One endpoint per operation, transport-focused dependencies, authenticated identity, and stable problem details.

## Agent Summary

- An API endpoint authorizes the target resource, not the actor. (standards/rule/backend-api.authorize-the-target-resource)
- The API returns RFC 7807 problem details on rejection. (standards/rule/backend-api.return-stable-problem-details)

**Rationale:** Two routes for one operation make authentication and authorization decisions ambiguous. Routing rules cannot tell which one to apply.

**Evidence:** `node tools/validate-standards.mjs` rejects a second route declaration.

**Example:** A POST to `/orders` and a POST to `/api/orders` both create orders. The second declaration is a violation.

### Keep endpoint dependencies transport-focused (standards/rule/backend-api.keep-endpoint-dependencies-transport-focused)

...

## Conventions

...

## Verification

| ID | Method | Evidence |
|:---|:---|:---|
| standards/rule/backend-api.use-one-endpoint-per-operation | static | `node tools/validate-standards.mjs` rejects a second route declaration. |
```

The Agent Summary lists every provision with `tier: high`, in `order`. The Verification table is one row per provision. The Standards and Conventions sections are the same provisions in the same order, fully expanded. The duplication is gone.

## Format choices

### Why YAML frontmatter

YAML is more human-friendly than JSON for the frontmatter. No quote noise. No trailing commas. Comments with `#`. Lists and maps with minimal syntax. Every modern LLM reads and writes YAML fluently. Tools that handle the JSON-Schema-metadata-block pattern handle YAML frontmatter natively.

The JSON output the validator and AI consume is produced by parsing YAML. The author never sees the JSON.

JSON as a body format is the path the user correctly called "diabolical." YAML as a frontmatter is the path that is human-friendly.

### Why Markdown body

Markdown is the format LLMs and humans are most comfortable with. It diffs cleanly. It renders in every documentation tool. The body of a provision is prose. Markdown carries all of it natively with no escape noise.

The blockquote-with-label pattern is the only non-standard convention the renderer adds. It survives every renderer the team has tested, and the parser is trivial: a blockquote whose first line matches one of three label prefixes.

### Why blockquote labels and not fenced code blocks

A fenced code block with a custom info string after the opening fence would also work. The blockquote-with-label pattern was chosen for three reasons.

A blockquote renders with a vertical bar that visually distinguishes it from prose, without looking like code. A fenced code block risks being syntax-highlighted by the renderer, which is wrong for prose content. The blockquote label is the first line of the blockquote, which means a Markdown reader sees `> Evidence:` immediately and knows what follows.

The trade-off is that some Markdown renderers add a vertical bar of variable width depending on nesting. This is acceptable for a documentation surface. If PDF export becomes a requirement, fenced blocks may be the right answer.

### What about JSON, TOML, AsciiDoc

JSON is the wrong shape for prose-heavy fields. The author would write a provision as a JSON object, escaping newlines for the rationale and example. Painful.

TOML is better for config but worse for nested rich content. Limited support for multiline strings. No advantage over YAML.

AsciiDoc has better primitives but worse tooling support and worse LLM fluency. A v3 candidate if Markdown proves insufficient.

The recommended path uses Markdown because it is the lowest-friction format for the author. If author friction becomes unacceptable, AsciiDoc is the migration target.

## Tooling choices

### The CLI

A single binary replaces the five current Node scripts. The subcommands.

`validate` runs all checks against a project directory. Default is every check. Flags filter to specific kinds.

`render` walks the contract and emits Markdown plus HTML. `--diff` shows what would change without writing. `--check` exits non-zero if rendered output differs from committed.

`query` finds provisions. Filters cover area, kind, tier, module, text. Returns JSON. Pipeable.

`publish` cuts a new release. Reads the contract, runs validators, renders outputs, bumps version, tags, publishes to npm and NuGet, deploys hosted docs.

`migrate` takes a consumer's `standards.project.json` and a target version. Reports changes. Optionally auto-edits compatible changes.

`doctor` checks the standards repo itself. Contract renders match committed Markdown. Schemas are valid. Validator tests pass.

`init` creates a consumer project skeleton from a profile.

### Distribution of the CLI

`npx @litenova/standards validate ./src` for npm consumers. `dotnet tool install Litenova.Standards` for .NET consumers. Native binaries from GitHub releases for other ecosystems. `docker run litenova/standards validate /workspace` for sandboxed CI.

The same CLI binary is published to all four channels.

### The library architecture

```
packages/
  core/           # Contract data + query API
  validator/      # All validation rules
  renderer/       # Markdown + HTML renderers
  cli/            # CLI wrapper
  mcp-server/     # MCP wrapper
  sdk-js/         # JavaScript SDK for embedding
  sdk-dotnet/     # .NET SDK for embedding
```

`core` exposes a single API: `load(contractDir)`, `query(filters)`, `get(id)`, `supersedes(id)`, `supersededBy(id)`. The validator and renderer consume `core`. The CLI calls the validator. The MCP server calls `core` for read paths and the validator for write paths.

### The MCP server

The MCP server exposes the contract via resources and tools. An agent operating on a consumer project queries the MCP server for exactly the rules that apply.

Resources. `standards://provisions` is the full index. `standards://provisions/{id}` is one provision with full text. `standards://manifest` is the current manifest. `standards://schema/{name}` is any consumer schema. `standards://prose/{page}` is the rendered prose for a page.

Tools. `get_applicable_provisions(module, kind)` returns provisions binding to a module. `validate_command_metadata(metadata)` validates a command metadata block. `find_overrides(consumer_manifest)` lists provisions a consumer has overridden. `supersession_chain(id)` walks the supersedes chain.

Prompts are templated agent interactions. "Review this code against backend standards." "List rules for an audit-record-emitting command." "What changed in this release that affects module X?"

### The HTTP API

The HTTP API mirrors the MCP server for tools that cannot use MCP. Same resources, same queries, JSON over HTTP. Authenticated by an API key issued on `init`. Rate-limited per consumer. Versioned under `/v2/`.

## Distribution and versioning

### Packages

The npm package `@litenova/standards` contains the JSON-rendered contract, the raw Markdown source, the schemas, the CLI entry point, the compiled JS, and the package metadata.

The NuGet package `Litenova.Standards` contains the same payload for .NET consumers, with a `dotnet tool` manifest.

GitHub releases publish native binaries for Linux, macOS, and Windows (amd64 and arm64), plus source archives and SHA-256 checksums.

Docker Hub publishes `litenova/standards:<version>` with the CLI pre-installed.

### Versioning: honest SemVer

v1 follows SemVer-style version numbers but does not guarantee compatibility. The contradiction costs consumer trust. v2 follows SemVer honestly.

Patch covers bugfixes to validator, renderer, or contract corrections that do not change a requirement's behavior. Example: `2.0.0` to `2.0.1` fixes a regex in the prose measure without changing the rule.

Minor covers additive changes. New optional fields. New provisions that do not contradict existing ones. Example: `2.0.0` to `2.1.0` adds a Deviation block to the provision body grammar; existing provisions without it still validate.

Major covers changes that require consumer action. Schema field removed or renamed. A rule's MUST becomes MUST NOT. Example: `2.0.0` to `3.0.0` removes `applicableExtensions` from the consumer metadata block; consumers must remove it before upgrading.

The CLI's `migrate` subcommand handles major upgrades. It reads the consumer's manifest, reports changes, optionally auto-edits compatible changes, and prints manual steps for breaking changes.

### Consumer pinning

Consumers pin via package managers. npm: `"@litenova/standards": "2.1.0"` in `package.json`. NuGet: `<PackageReference Include="Litenova.Standards" Version="2.1.0" />` in the `.csproj`.

The CI installs the pinned package. The CLI reads the pinned version. Adopting a later version is changing the pin and running `migrate`.

### Hosted docs

The hosted docs are at a versioned URL. On every release: render the contract to HTML, publish to the versioned URL, redirect from `/latest/` and `/<major>/`.

Search is built in. The page metadata, provision IDs, and rendered prose are all searchable.

## The operational surface

The MCP server, the HTTP API, the hosted docs, and the publishing pipeline form the operational surface. They run the system the contract holds. The next sections describe the MCP server, the HTTP API, the hosted docs, the deployment, the CI/CD pipeline, the observability, the security model, the lifecycle, the cost, and the disaster recovery.

### The MCP server

The MCP server is the architectural payoff of v2. An agent operating on a consumer project queries it for exactly the rules that apply. It does not read a hand-maintained Agent Summary projection. It queries structured data.

The server exposes three transports. Stdio is the default for local development. The server reads the contract from a local path. No network calls. Lowest latency. Streamable HTTP is the default for hosted use, speaking MCP over HTTP with Server-Sent Events for streaming responses. Server-Sent Events alone is a fallback for clients that do not support streamable HTTP. A single server binary serves all three transports. The active transport is determined by configuration.

Three authentication modes exist. Anonymous is the default for the local stdio server. No key. The server reads whatever contract the local path points to. Per-consumer API key is the default for the hosted HTTP server. A consumer receives a key on `init` and passes it as `Authorization: Bearer <key>`. The key maps to a consumer record with rate limits, a pinned version, and audit settings. Per-agent scoped token is an option for multi-agent consumers. A consumer issues scoped tokens to its agents. Each token contains the consumer's pinned version and an agent identifier for audit. The token has a lifetime independent of the API key.

Resources are addressable. Each has a stable URI. The `standards://provisions` URI returns the full index of provision IDs in the pinned version. The `standards://provisions/{id}` URI returns one provision with full text. The `standards://manifest` URI returns the pinned manifest. The `standards://schema/{name}` URI returns one of the 10 consumer schemas. The `standards://prose/{page}` URI returns the rendered prose for a page. Resources are read-only. Mutations are tools.

Six tools are exposed. `get_applicable_provisions(module, kind)` returns provisions binding to a module. `validate_command_metadata(metadata)` validates a command metadata block. `find_overrides(consumer_manifest)` lists overridden provisions. `supersession_chain(id)` returns the chain in order. `diff_versions(from, to)` returns the change set between versions. `render(page, format)` renders a page in Markdown or HTML.

Prompts are templated agent interactions, not tools. `review_against_backend` opens a prompt asking the agent to review code against the backend standards. Relevant provisions are pre-loaded. `audit_command_obligations` opens a prompt for an audit-record-emitting command. Audit extension provisions are pre-loaded. `migration_diff` opens a prompt summarising contract version changes for a module.

Error handling uses JSON-RPC error codes per the MCP specification. Validation errors return code -32602. Authorization errors return -32003. Rate limit errors return -32004. Method not found returns -32601. Each error carries a `data` field with severity, location, message, and a short suggested_fix string.

The server reports its protocol version during the MCP `initialize` handshake. The contract version is reported via the manifest resource. Breaking changes to the MCP API require a major version bump of the standards package. The server supports the previous major for one year after a new major releases.

A consumer's MCP client configuration adds the standards server. The config includes the command, the arguments, and an environment variable carrying the API key. The agent invokes the server through MCP. The server returns structured data. The agent applies it to the consumer's code.

Local mode exists for consumers who want MCP without a hosted account. The command is `litenova-standards mcp serve --contract=./contract`. The server reads the contract from disk. No authentication. No telemetry. Useful for offline development and for CI runs that want MCP without network.

### The HTTP API

The HTTP API mirrors the MCP server for tools that cannot use MCP. Same resources, same queries, JSON over HTTP.

The API is resource-oriented. The provisions endpoint lists provisions. The provision-by-id endpoint returns one provision. The manifest endpoint returns the manifest. The schema-by-name endpoint returns a schema. The page-by-path endpoint returns the rendered prose. Query parameters apply filters by area, tier, and kind.

Authentication is the same as the MCP server. The `Authorization` header carries the bearer key. Anonymous access is disabled on the hosted HTTP API. Local mode bypasses authentication.

Rate limiting uses a token bucket per consumer. Default 60 requests per minute. Configurable per consumer tier. The bucket is keyed on the API key. Rate-limited responses return HTTP 429 with the `Retry-After` header and the standard error envelope.

Pagination is cursor-based. List endpoints return a `next_cursor` field when more results exist. The cursor is opaque to clients. Default page size is 100. Maximum is 1000.

Error format is RFC 7807 problem details. Each error response carries `type`, `title`, `status`, `detail`, and `instance`. Extensions add `severity`, `location`, and `suggested_fix`. The format is generated from the same contract schema the renderer uses for the CLI.

The OpenAPI specification for the HTTP API is generated from the contract. The schema is derived from the contract's structured fields. Paths are derived from the resource URIs. The OpenAPI document is published at a versioned URL and rendered to HTML at the same path with `.html`.

ETags apply on every GET response. `Cache-Control: public, max-age=300` covers resources that change at release boundaries. The CDN adds edge caching with `s-maxage=86400` for stable resources. Mutations are not cached.

Mutating endpoints accept an `Idempotency-Key` header. A consumer can safely retry a mutating request with the same key within 24 hours. The server stores the response and returns it on retry without re-executing.

### Hosted documentation

The hosted docs are the human-readable view of the contract, generated on every release.

The CLI's `render --format=html` emits one HTML file per page plus an index. The build is deterministic. Same contract, same HTML. The build runs in CI on every tag.

Hosting uses a static site on a CDN. Any provider supporting static hosting and edge redirects works. The design assumes Cloudflare Pages, Netlify, or AWS CloudFront plus S3 as compatible targets. The CDN handles TLS, edge caching, and DDoS protection.

Search uses a client-side index. No server. The index is built at the same time as the HTML. The search covers page titles, provision IDs, requirement text, and rationale text. The index is small enough to ship in the static bundle. Under 1 MB for the full contract.

Version routing follows the pattern `/Standards/v{version}/{area}/{page}`. The `/Standards/latest/` URL redirects to the newest tagged version. The `/Standards/{major}/` URL redirects to the newest minor of that major. Old versions stay reachable indefinitely.

A new release adds new URLs. Old URLs from the previous version keep working through HTTP 301 redirects. The redirects are computed at build time and shipped as static files.

Analytics is privacy-respecting. Page view counts via a first-party beacon. No third-party trackers. No personal data. Aggregated by version and area. Used to identify which pages are read and which are not.

Accessibility targets WCAG 2.1 AA. Semantic HTML in the rendered output. Skip-to-content link. Color contrast tested. Keyboard navigation. Screen reader labels on all interactive elements. Verified with axe-core in CI.

### Deployment topology

Three logical services run. The MCP server, the HTTP API, and the hosted docs. Each is deployed as containers. Each is stateless. State lives in object storage for the contract bundle, a managed database for consumer records and API keys, and a secret manager for signing keys.

Compute is containers on a managed Kubernetes service or a container service equivalent. The MCP server and HTTP API scale horizontally. The hosted docs are static and need no compute.

Regions: the MCP server and HTTP API run in multiple regions. Three at launch: EU, US, Asia. Latency under 100 ms for the majority of consumers. The hosted docs are served by a global CDN with edge caching.

Configuration is environment variables loaded from a secret manager at startup. No secrets in the repository. No secrets in container images. The contract bundle is fetched from object storage on startup and refreshed on a signal.

Secrets: API signing keys, consumer key hashes, and rate-limit bucket salts live in the cloud secret manager. The MCP server and HTTP API read them at startup. Keys have a 90-day lifetime with zero-downtime rollover.

Multi-region is active-active for the MCP server and HTTP API. The same binary image runs in every region. Consumer requests route to the nearest region via geo-DNS. Consumer records replicate across regions via async replication with eventual consistency.

Storage is object storage for the contract bundle. A managed Postgres for consumer records. A managed Redis for rate-limit buckets. All three are managed services, not self-hosted.

Networking is TLS 1.3 for all transports. HTTP/2 for the HTTP API. HTTP/3 where the CDN supports it. No plaintext. mTLS between services inside the cluster. Network policies restrict egress to known endpoints.

### CI/CD for the standards repository

The standards repository has its own CI/CD. The pipeline runs in GitHub Actions or an equivalent.

On every commit: contract validate, prose measures, schema validity, provision ID resolution, link checker. All checks must pass before merge.

On every PR: same checks plus a render diff. The PR shows what the rendered Markdown and HTML would look like. Reviewers see the visual change. The contract is still authored in YAML plus Markdown. The rendered output is the diff surface.

On tag creation: full build, package publish to npm and NuGet, Docker image publish, hosted docs deploy, MCP and HTTP API deploy. The tag is the source of truth. The release is whatever the tag points at.

On schedule: weekly dependency updates, monthly security scans, quarterly license audits, and an annual review when v3 begins.

Branch protection: main is protected. PRs require one approval from a code owner plus a passing CI. Squash merge. Linear history. The commit on main matches the deployed state at every moment.

Signing: all commits and tags are signed. Consumers verify the signature when installing a package. The signing key is held by the release engineer. Rotation follows the secret rotation cadence.

### Observability

The operational surface is covered by structured logs, metrics, and traces.

Logs are JSON. Every request contains a request ID. Every MCP query contains the consumer key hash, not the key itself, and the agent token ID if any. Logs are queryable by request ID, consumer, version, and time range.

Metrics cover request rate, latency p50, p95, p99, error rate, and cache hit rate. Per endpoint and per consumer. The MCP server exposes these via a `/metrics` endpoint in Prometheus format. The HTTP API does the same.

Traces are distributed. They follow a request from the CDN edge through the HTTP API or MCP server. The traces continue through the renderer and out to the consumer. Span IDs are propagated. Traces are sampled at 10% for high-volume consumers and 100% for errors.

Dashboards report usage by consumer, usage by version, usage by area, most-quoted provisions, and most-queried pages. These dashboards inform the standards authors which parts of the contract are read and which are not.

Alerts cover error rate spikes, latency p99 regressions, validator regressions in CI, cache hit rate drops, and disk usage on the contract bundle. Each alert has a runbook in the operations repository. Each alert has an escalation path on the on-call rotation.

### Security model

Three threat actors target the system. Malicious consumers trying to scrape the contract. Malicious agents trying to bypass the contract. Infrastructure attackers trying to compromise the hosted services.

API keys are bearer tokens. They are hashed at rest, with SHA-256 plus salt. Each key has a 90-day lifetime. The previous key remains valid for 7 days during rotation. A leaked key is revoked immediately and the consumer is notified.

Rate limits per consumer default to 60 requests per minute. Configurable per consumer tier. Burst capacity is 2x the steady-state rate. Sustained abuse leads to automatic key suspension and a manual review.

An audit log entry is written for every MCP and HTTP API call. The log contains the consumer key hash, the agent token ID, the query type, the resource URI or endpoint, and the response status. The log is retained for 90 days. The log is queryable by consumer for their own activity. Operators query the log for incident response.

No PII appears in logs. Logs contain consumer key hashes and agent token IDs. They do not contain the keys themselves, the tokens themselves, or any payload from the consumer's code. An agent that sends its code for review is not logged. The query type and the relevant provision IDs are.

TLS is applied to all transports. TLS 1.3 for all transports. HTTP/2 for the HTTP API. HSTS with preload. Certificate transparency is monitored.

Threat modeling is documented in the security model. Updated quarterly. Reviewed by an external party annually. The threat model lists assets, attackers, attack vectors, and mitigations.

Incident response follows a runbook in the operations repository. Severity levels. Escalation paths. Communication templates. Postmortem template. The team practices the runbook quarterly.

### Lifecycle: versioning across channels

Package, docs, MCP, HTTP API, and OpenAPI all use the same version. The version is embedded in URLs and resource URIs.

Version embedding: the npm package version is `2.1.0`. The NuGet package version is `2.1.0`. The hosted docs URL is `/Standards/v2.1.0/`. The MCP resource URIs include the version segment. The HTTP API URL is `/v2.1.0/...`. The OpenAPI document is at a versioned URL.

Pinning: a consumer's API key pins a major version. The MCP and HTTP API serve the pinned version. The consumer upgrades by issuing a new key with the new major. Vendored consumers pin via the package manager.

Rollback: every release keeps the previous version live indefinitely. Old versions stay reachable. Rollback is changing the pin or changing the package version.

### Backwards compatibility commitments

Backwards compatibility holds within a major version. Breaking changes require a major bump.

Within a major, changes are additive only. New fields in the contract. New endpoints in the API. New tools in the MCP server. New provisions. All backwards compatible.

Across majors, breaking changes are documented in the CHANGELOG. Changes are listed through the CLI's `migrate` subcommand and through the diff API between versions. Upgrades happen at the consumer's discretion.

Deprecation policy: when a feature is deprecated, announce at major N-1, support through major N, remove at major N+1. Three majors of overlap. For consumers on major N-2 when a removal happens at major N+1, the removal is announced in their pinned version. They have one major to upgrade.

API deprecation specifics: deprecated endpoints are marked with a `Deprecation` header per RFC 8594. A `Sunset` header is set with the removal date. The migration path is documented in the response body. Deprecated endpoints remain functional until sunset.

### Cost model

The operational surface is delivered as a managed service. Costs scale with usage.

Compute costs scale with the number of running instances times the per-instance cost. Three regions at launch. More added as usage grows.

Storage costs are small. Object storage for the contract bundle is under 100 MB total. Postgres for consumer records is under 1 GB at launch. Redis for rate-limit buckets is small.

Bandwidth costs arise mostly from CDN-served hosted docs. Per-page static HTML plus the search index. Roughly 10 KB per page. The total bundle is under 5 MB.

Per-request costs are cheap. Token validation, database lookup, contract query. Roughly 1 ms server time per request. The cost per request is fractions of a cent.

Tiers: a free tier covers local use and small consumers. The hosted MCP and HTTP API are paid above a threshold TBD. The hosted docs are free for all.

Forecasting is quarterly. Forecast updated against actuals. Capacity planning tied to the forecast. The cost is reported in the operations dashboard.

### Disaster recovery

The contract is in the Git repository. All channels regenerate from the contract. Recovery is rebuild-and-redeploy.

The Git repository is the source of truth. Every tag is a release. Every commit is auditable. The Git history is the backup.

If the hosted services are down, consumers fall back to the vendored package. The package contains the full contract plus the validator and renderer. Consumers can run validation offline. They lose MCP and HTTP API access until services recover.

Rebuild time from Git to deployed state is under four hours for a single region. Multi-region adds time for async replication. The runbook is in the operations repository.

Failover is active-active multi-region. A region outage routes consumers to the nearest healthy region via geo-DNS. Consumer records are eventually consistent. A brief window of stale data is acceptable.

Backups: Git tags are the backup. Object storage is replicated across regions. Postgres is backed up daily with point-in-time recovery. Redis is rebuilt from the contract on restart.

The runbook is documented in the operations repository. Step by step. Tested quarterly. The runbook covers region failure, contract corruption, key compromise, and rate-limit overflow.

## Dogmas: kept, changed, added, removed

### Kept

Controlled prose where it is enforceable: 25-word sentence, 20-word list cell, 6-sentence paragraph, no metaphors, ASCII only. These apply to the Markdown body of a provision file. The validator checks them.

The identifier grammar `standards/<kind>/<page>.<slug>` is unchanged.

The page contract per page class is unchanged in the rendered output.

One word per concept remains mechanically enforced through the language record and the consumer glossary.

The provision block shape is unchanged in the rendered output.

The closed normative vocabulary (MUST, MUST NOT, SHOULD, SHOULD NOT, MAY) is unchanged.

### Changed

No migration between standards releases becomes documented migration on major bumps. The complete-contract-per-release stance stays for minor and patch. Major versions get a `migrate` subcommand and a CHANGELOG entry.

Markdown is generated, not authored. The author writes the provision file. The renderer emits the page Markdown. The Markdown in `rendered/` is committed for diffability but is not the source.

The submodule is replaced by packages. Consumers depend on packages, not on cloning the repository.

The Agent Summary is generated from `tier: high`, not hand-written. The 700 redundant citation entries disappear.

The Verification table is generated from each provision's Method and Evidence. The 1500 redundant ID-column entries disappear.

Profile Composition and extension Baseline relationship are derived from the manifest. The manifest becomes the single source.

The Intent section is generated from `_page.yaml`. The 64 hand-written Intent sections disappear.

### Added

The tier field on provisions: `high`, `medium`, or `low`. The Agent Summary picks `high`; future tier-aware views use the others.

Blockquote labels for Evidence, Example, and Deviation. Three labels the parser recognises. Everything else is body prose.

Per-page `_page.yaml` manifests declaring page metadata and provision order.

Supersedes and supersededBy fields. Provisions form a versioned chain. The CLI walks the chain.

Distribution via npm, NuGet, Docker, native binary, MCP, and HTTP API. Six channels, one contract.

### Removed

The `templates/standard/` directory: the page-contract table in `authoring.md` is the template. Five files become zero.

Per-page Agent Summary hand-writing. The section is generated.

Per-page Verification table hand-writing. The table is generated.

The `docs/tools/` consumer-facing area. Moves to `docs/meta/` or disappears (the CLI is the new docs surface).

The submodule onboarding instructions in README. Replaced by package installation.

The vendor shim files for AI tools. Replaced by the MCP server entry point.

## Migration strategy

The migration is phased. Each phase ships independently. Each is reversible.

### Why phased

A single-step migration would require converting all 899 provisions at once, replacing the submodule with packages at once, switching the validator pipeline at once, and standing up the MCP server at once.

A phased migration lets the team validate the approach on one page before committing to all 100. It lets each phase be independently valuable and reversible.

### Phase 1: structured contract alongside Markdown

What ships: the `contract/` directory with one `.md` file per provision for a single page (`docs/core/agent.md`). The CLI's `validate --target=contract` works for that page. The existing `docs/core/agent.md` continues to pass the v1 validator.

What this proves: the per-provision Markdown model works for a real page. The YAML frontmatter is parseable. The blockquote labels are detectable. The renderer emits the same content as the hand-written page.

Exit criteria: the `agent.md` page in `contract/core/agent/` plus its `_page.yaml` produces a `rendered/core/agent.md` that diffs clean against `docs/core/agent.md`. The CLI's `validate --target=contract` exits 0 for that page. The author of the page has confirmed the per-provision authoring model feels natural.

### Phase 2: structured contract for all pages

What ships: `contract/` fully populated for all 100 pages. The CLI works for all pages. The v1 `docs/` directory remains, with the duplication existing twice.

What this proves: the model scales beyond one page. The validation rules work on every page. The blockquote-label grammar covers every case in the corpus.

Exit criteria: every Standards and Conventions H3 in `docs/` has a corresponding provision file in `contract/`. The CLI exits 0 across the full corpus. A reviewer has compared 10 randomly sampled rendered pages against the hand-written originals and found no meaningful differences.

### Phase 3: Markdown generated, not authored

What ships: the CLI's `render` subcommand emits Markdown for the full corpus to `rendered/`. The `docs/` directory is replaced by `rendered/`. CI runs `litenova-standards render --check` to catch contract edits that forgot to regenerate.

What this proves: the rendered Markdown is acceptable as the published contract. The duplication is gone.

Exit criteria: `rendered/` and the previous `docs/` produce identical output for the full corpus. `render --check` exits 0 on a clean contract. The team has agreed that the rendered Markdown is acceptable as the published prose.

### Phase 4: package distribution

What ships: npm package published on every release. NuGet package published on every release. Native binaries published to GitHub releases. Docker image published to Docker Hub. Claimwick migrates from submodule to package. Submodule instructions removed from README.

What this proves: the package distribution works for a real consumer. The migration from submodule to package is straightforward.

Exit criteria: `npm install @litenova/standards@2.0.0` works in a clean project. `dotnet tool install Litenova.Standards --version 2.0.0` works. `docker run litenova/standards:2.0.0 validate /workspace` works. Claimwick's CI runs against the package and the submodule is removed.

### Phase 5: hosted docs and MCP server

What ships: rendered HTML hosted at a versioned URL. Versioned URLs with redirect from `/latest/` and `/<major>/`. Client-side search. MCP server. HTTP API. Per-page Agent Summary sections removed from the rendered output (the agent queries instead).

What this proves: the agent affordance is the architectural payoff. An agent operating on a consumer project can ask the contract precise questions and get precise answers.

Exit criteria: hosted docs URL resolves at the versioned path. Search finds a known provision by ID. MCP server responds to `resources/list` and `tools/call`. HTTP API returns the same data for the same query.

### Order of operations

The phases depend on each other. Phase 1 must ship before Phase 2 (you cannot scale what you have not proved). Phase 2 must ship before Phase 3 (the renderer cannot replace `docs/` until `contract/` covers everything). Phase 3 must ship before Phase 4 (you cannot publish a package that depends on the contract until the contract is canonical). Phase 4 must ship before Phase 5 (the agent affordance reads from the canonical package, which only exists after Phase 4).

Phases 1 and 5 are the highest value. Phase 1 proves the model; Phase 5 is the payoff.

### Reversibility

Each phase is reversible.

Phase 1: delete `contract/` and the new CLI subcommand. v1 still works.

Phase 2: revert `contract/` to a partial population. v1 still validates the hand-written pages.

Phase 3: revert to hand-written `docs/`. The contract remains authoritative for the validator.

Phase 4: revert to submodule distribution. The package remains as an additional channel.

Phase 5: revert to Agent Summary sections in rendered Markdown. The MCP server remains as an additional channel.

## Open questions

These are the questions still to settle before Phase 1 begins. They are ordered by how much they block the work.

### Blocking for Phase 1

1. Naming. The system is named inconsistently today (`Engineering-Standards` in the repo, "Agentic Engineering System" in the README hero, "Engineering Standards Agent Protocol" in AGENTS.md). The package names, hosted URL, MCP server name, and CLI command all follow from the chosen name. Decide before Phase 1.

2. One file per provision vs one file per page. The recommendation is one file per provision. If authors reject the file count, the fallback is one file per page with structured section blocks. Decide before Phase 1.

3. Frontmatter field set. Confirm the schema. The proposed set is `id`, `kind`, `area`, `page`, `slug`, `tier`, `method`, `supersedes`, `supersededBy`. Decide before Phase 1.

4. Blockquote label set. Confirm three labels: `Evidence:`, `Example:`, `Deviation:`. Decide before Phase 1.

5. Page metadata set. Confirm `area`, `page`, `title`, `intent`, `order`. Decide before Phase 1.

### Blocking for Phase 2

6. Honest SemVer stance. Confirm patch = bugfix, minor = additive, major = breaking with documented migration. Decide before Phase 2.

### Blocking for Phase 4

7. Hosted docs URL. Confirm the versioned URL pattern. Decide before Phase 4.

8. Migration of Claimwick consumer. Confirm Claimwick migrates from submodule to package in Phase 4. Decide before Phase 4.

### Open in principle

9. ASCII only rule. The rule serves diff stability. Keep for the standards contract; consider relaxing for consumer-facing docs.

10. No metaphors rule. The current implementation rejects all figures of speech. The rule's intent is to refuse metaphors that assert ordering the prose does not have. Soften to "metaphors allowed when they earn their keep, refused when they assert ordering." Reviewer judgment, not validator enforcement.

11. No contractions rule. Full forms only. Consider contractions for consumer-facing docs, keep full forms for the standards contract.

## What success looks like

### For authors

A contributor adds a provision by writing one Markdown file. The renderer regenerates the page. The validator passes. The release publishes the package. The hosted docs reflect the change. The MCP server returns the new provision. All from one commit. The diff is one file, one rule, one assertion.

### For readers

A reader of the hosted docs finds a provision by ID, by title, or by full-text search. The reader sees the rendered Markdown. The reader does not need to know JSON, YAML, or any contract format.

### For consumers

A consumer installs the package with one command. The CI runs the validator. The consumer upgrades with the package manager; nothing breaks on minor and patch; the `migrate` subcommand guides major upgrades. The submodule is gone.

### For agents

An agent operating on a consumer project asks the MCP server "what rules bind to this command?" and gets the precise list. The agent applies them. The agent does not read prose projections; it queries structured data.

### For the contract

The duplication in v1 is gone. Each provision lives in one place. The Markdown, HTML, JSON, and MCP views are all derived. The contract is canonical. The views are views.
